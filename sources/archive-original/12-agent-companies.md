# Agent companies: how their products are built and how their businesses work

Scope note (written 21 November 2026). This file covers the companies that sell AI agents doing a defined job for a business: customer-service agents (Sierra, Decagon, Fin by Intercom, briefly others), professional-work agents (Harvey, Hebbia, Abridge), internal or "AI employee" agents (Glean, Ramp, Lindy, Manus), delivery-led firms (Distyl), sales agents (11x), and Chinese agent platforms (Coze Studio, Dify, Tencent ADP). It goes deepest on Sierra and Harvey. The aim is design input for a product that holds a company's model (objects, metrics, rules, permissions, actions) so agents work through it. Every claim is labelled: [Fact] (checked against a primary source or code), [Vendor claim] (the company says it, not independently checked), [Inference] (my reasoning), [Unverified] (I could not find or open a source). Research limits: partway through, the shared web-search budget (200 calls) and then the web-fetch budget ran out. After that I used direct fetches of known pages, one every few seconds, and cloned repositories. Several of the smaller companies (Cresta, Ada, Parloa, PolyAI, Rogo, Writer, Artisan, Baidu, Zhipu, ByteDance HiAgent's product page) are therefore thin or marked unverified. I say so where it applies.

## Key findings

1. **The winning knowledge layer is a written procedure plus deterministic guardrails plus typed tool connections, not a model fine-tune.** Sierra calls these journeys and guardrails, Decagon calls them Agent Operating Procedures (AOPs), and Fin calls them Procedures. All three let a non-engineer write the procedure in plain language. Where the rule is hard (a 30-day return window, an eligibility check, a date calculation), they add code or deterministic checks. [Fact] https://sierra.ai/blog/agent-development-life-cycle ; https://decagon.ai/product/aop ; https://fin.ai/procedures
2. **Sierra's no-code journeys are a declarative DSL that compiles deterministically to Agent SDK code.** Builders can therefore move between no-code and Git. Its build agent, Ghostwriter, writes that DSL and needed tuning because the DSL is not in model training data. [Vendor claim, secondary summary of a Sierra talk] https://www.zenml.io/llmops-database/building-production-scale-voice-and-multi-modal-customer-experience-agents
3. **Every serious vendor treats an agent change like a code release.** The release is an immutable snapshot of code, prompts, model versions and a frozen copy of the knowledge. It moves through QA, staging and production, can be rolled back instantly, can be A/B tested or split-traffic released, and is gated on simulations and named reviewers. [Fact/Vendor claim] https://sierra.ai/blog/agent-development-life-cycle ; https://sierra.ai/blog/agent-studio-2-0 ; https://www.unite.ai/es/sierra-puts-ghostwriter-at-the-center-of-agent-studio-workflows/
4. **Testing means simulating users against mocked systems and checking the end state.** The public reference design is Sierra's tau-bench. An LLM plays the user from a task instruction. The agent gets tools and a written policy. Success means the final database state equals the state produced by replaying a reference action list, and required facts were communicated. Reliability is measured with pass^k = C(successes, k) / C(trials, k). [Fact, code read] /home/claude/research/_code/tau2-bench/docs/evaluation.md ; https://arxiv.org/abs/2406.12045
5. **Production failures turn into regression tests.** Sierra turns each annotated bad conversation into a simulated test against mock APIs. Customers run more than 35,000 tests a day. Simulations can be run from GitHub Actions or a CLI and can gate releases. [Vendor claim] https://sierra.ai/blog/agent-development-life-cycle ; https://sierra.ai/blog/simulations-the-secret-behind-every-great-agent
6. **The improvement loop is now itself an agent, but humans approve every change.** Sierra's Ghostwriter (25 Mar 2026; teammate in Slack and Teams 28 Sep 2026; Agent Studio rebuilt around it 2 Nov 2026) and Decagon's Duet Autopilot (9 Jun 2026) both work the same way. They detect issues from 100% of conversations, trace the root cause, draft a change in an isolated session or branch, test it in simulation against the originating conversation plus a golden set, and wait for human approval and merge. [Vendor claim] https://sierra.ai/blog/redesigning-agent-studio-around-ghostwriter ; https://decagon.ai/blog/autopilot
7. **Outcome pricing works only where the agent is autonomous and the outcome is attributable.** Sierra agrees the outcome definition with each customer up front. Unresolved and escalated conversations are usually free. Routing or greeter traffic is billed per conversation. Some sales agents earn a commission. Fin publishes the cheapest version: $0.99 per outcome, where a resolution means the customer asks for no further help after Fin's last answer, billed at most once per conversation. [Fact/Vendor claim] https://sierra.ai/blog/outcome-based-pricing-for-ai-agents ; https://sierra.ai/blog/outcomemaxxing ; https://fin.ai/pricing
8. **Harvey sells seats, not outcomes, and has grown about as fast.** Sacra estimates Harvey at about $1,200 per lawyer per month, with 12-month terms and about 20-seat minimums, and puts ARR above $400M in August 2026. Professional work-product is hard to attribute as a single outcome, so seats fit. [Vendor/analyst estimate] https://sacra.com/c/harvey/
9. **Permissions must be enforced on the retrieval path and again before any content reaches the model.** Harvey's ethical-wall design is the most detailed public example. Matters are linked to resources. Walls are inclusionary or exclusionary. Membership sets are content-hashed and immutable. A search index that holds no wall data is filtered and then re-checked against the stored policy, because the index is eventually consistent. Agents run as their creator. Unauthorised items look as if they do not exist. Admins get no bypass. [Fact] https://www.harvey.ai/blog/building-ethical-wall-enforcement-into-harvey
10. **Tool calls by agents need their own policy engine that never sees the data.** Harvey evaluates every MCP tool call with Rego policies, embedded in-process. The inputs are tool identity, a Harvey-written risk annotation, capability flags and the names of prior calls. Arguments and free text are excluded. The engine fails closed, can pause the call for user approval, and pins tool descriptions and schemas to detect changes. [Fact] https://www.harvey.ai/blog/building-harveys-mcp-policy-engine ; https://www.harvey.ai/blog/how-we-built-harvey-connector-library
11. **A pre-built, source-linked graph beats retrieval-only agents on table-heavy enterprise questions.** Distyl's Context Views scored 84.4% exact-match at $0.11 per question on OfficeQA Pro V2, against 38.9% for the best search agent. Hebbia reports 80% lower cost than a frontier model without its graph. Both resolve entities and record provenance at ingestion rather than at question time. [Vendor claim] https://www.distyl.ai/blog/research/context-views-what-a-knowledge-graph-buys-an-agent ; https://www.hebbia.com/blog/building-a-knowledge-graph-for-financial-institutions
12. **Deployment speed comes from people plus packaged starting points.** Sierra pairs agent engineers with agent product managers (titled "Product Manager, Agent Development"). Decagon pairs agent product managers with agent deployment engineers. Both now ship prebuilt, updatable packages: Sierra's Accelerators (5 Nov 2026), for example retention, first-notice-of-loss intake and patient authentication. Reported time to live: 27 days for a $40B+ retailer, seven weeks for a large healthcare company, under 10 weeks for Singtel. [Vendor claim] https://sierra.ai/blog/our-customers-ambition-is-accelerating-our-growth ; https://sierra.ai/blog/year-two-in-review ; https://sierra.ai/blog/accelerators ; https://decagon.ai/blog/agent-deployment-engineering
13. **Expansion follows one path: support, then actions, then revenue, then long-running outcomes.** Sierra went from answers to memory and actions (Agent OS 2.0, Nov 2025), then to Horizon (Jul 2026, agents pursuing a loan or a prior authorisation over days or weeks). Decagon launched Missions (Nov 2026). Harvey went from chat to cloud agents that work over hundreds of thousands of documents. [Vendor claim] https://sierra.ai/blog/horizon ; https://www.harvey.ai/blog/why-we-built-our-own-cloud-agent-infrastructure
14. **The visible failure is the AI SDR (sales development representative).** TechCrunch (24 Mar 2025) reported that 11x counted ARR on one-year contracts with three-month break clauses. One employee estimated $14M reported against about $3M surviving the break period. Staff described 70 to 80% churn and a product that "barely works". Open-ended outbound work with no attributable outcome and no customer-specific procedure layer failed. [Fact, reporting] https://techcrunch.com/2025/03/24/a16z-and-benchmark-backed-11x-has-been-claiming-customers-it-doesnt-have/
15. **Multi-model routing and zero data retention are table stakes for regulated buyers.** Sierra uses 15+ models, with failover on latency, errors and timeouts. Harvey built its own agent runtime because managed runtimes from the model labs did not meet zero-data-retention or multi-model needs. Harvey reports 3 to 5x lower cost from routing each task to the cheapest model that meets a quality threshold. [Vendor claim] https://sierra.ai/blog/constellation-of-models ; https://www.harvey.ai/blog/why-we-built-our-own-cloud-agent-infrastructure

### Sierra Agent OS (1.0 to 2.0) and the Agent SDK

Plain English. Agent OS is the runtime and the tooling. The SDK is how engineers write an agent as code. You declare goals ("help a customer return an order") and guardrails the agent cannot cross ("30-day window"), and the platform decides how to reach the goal.

Technical detail:
- The SDK is a "declarative programming language". Agents are composed from skills that encode procedural knowledge. Developers declare goals and deterministic guardrails. Guardrails are enforced deterministically in high-stakes actions such as processing an order or upgrading a plan. Behaviour is abstracted from the LLM, so models can be swapped without code changes. [Vendor claim] https://sierra.ai/blog/agent-development-life-cycle
- Out-of-the-box skills include triage, respond and confirm. A knowledge engine holds FAQs and policies. Escalation hands off to the contact centre with an auto-generated summary. Ramp's testimonial calls this writing "customer journeys as code". [Vendor claim] https://sierra.ai/product/agent-sdk
- Agent engineers can bypass the LLM to emit exact regulated language, build custom supervisors for healthcare or finance, and encode regional policy (UK vs US). The SDK enforces deterministic API interactions with systems of record. [Vendor claim] https://sierra.ai/blog/meet-the-ai-agent-engineer
- Agent OS 2.0 (5 Nov 2025) adds: build once and deploy to chat, voice, email, SMS, ChatGPT and the contact centre; Live Assist for human agents; Agent Studio 2.0 (journeys, workspaces, Integration Library); Insights 2.0 (Explorer, and Expert Answers, which turns contact-centre expertise into grounded articles); and the Agent Data Platform. [Vendor claim] https://sierra.ai/blog/agent-os-2-0
- Payments run on an isolated PCI DSS Level 1 cluster, so card data never reaches external LLMs. Sierra prefers one monolithic agent per customer to a multi-agent split, and supports MCP and agent-to-agent protocols. [Vendor claim, secondary] https://www.zenml.io/llmops-database/building-production-scale-voice-and-multi-modal-customer-experience-agents

### Sierra journeys (the declarative language) and how it compiles

Plain English. A journey is a no-code description of one customer goal, such as "cancel subscription". It lists the policies to obey, the tools allowed and what to do next, built from blocks rather than a flowchart.

Technical detail:
- Journeys are built from composable building blocks. Sierra contrasts this with sequential workflows and SOP lists, which it says degrade as they grow. The blocks are the same ones engineers use in the SDK. [Vendor claim] https://sierra.ai/blog/agent-studio-2-0
- Journeys are a declarative DSL that compiles deterministically to Agent SDK code, so teams can round-trip between no-code and code, including Git workflows. Journeys have been the main build interface for about 18 months. [Vendor claim, secondary summary of a Sierra talk; the talk itself not watched] https://www.zenml.io/llmops-database/building-production-scale-voice-and-multi-modal-customer-experience-agents
- I found no public syntax, schema or compiler description. [Unverified]

Inference for the founder: the value is the single representation. A business user edits the same artifact engineers version and test. A no-code layer that cannot round-trip to code splits the team.

### Agent Studio and Ghostwriter (25 Mar 2026 to the 2 Nov 2026 redesign)

Plain English. Agent Studio is the web app where support and ops staff build, test and release agents. Ghostwriter is an agent inside it that builds and fixes the customer's agent. You upload your SOP PDF and some call recordings, and it drafts the journeys and the tests.

Timeline and mechanics:
- **Agent Studio 2.0 (Nov 2025).** Each person edits in a private workspace. Journeys, configuration and simulations are versioned automatically. Ready changes combine into numbered snapshots that move QA, then staging, then production, with full history and instant rollback. The Integration Library flow is: pick an integration, add credentials and endpoints, publish. The connection then exposes tools usable in both Studio and the SDK, and developers can write their own. [Vendor claim] https://sierra.ai/blog/agent-studio-2-0
- **Ghostwriter launch (25 Mar 2026, "Agents as a Service").** Inputs: SOPs, process documents, call transcripts, whiteboard photos, audio and plain-English goals. It identifies key behaviours and edge cases. It edits journeys, writes integrations, creates simulations and triages issues, testing changes in a sandbox before they go live. To make this possible Sierra rebuilt itself as headless infrastructure that Ghostwriter operates through an agent harness (tools, memory, planning, context). [Vendor claim] https://sierra.ai/blog/agents-as-a-service. It also ingests PDFs, recordings and zip files of logs, tickets and training documents. [Vendor claim] https://sierra.ai/blog/how-customer-teams-became-software-builders
- **Teammate mode (28 Sep 2026).** Ghostwriter joins a Slack or Teams channel. It reports trends on request, proactively suggests experiments, and announces when an experiment reaches statistical significance. It reflects weekly on its engagement and stays quiet unless it has something useful to say. In one example it replaced a week-long manual call review: it proposed three changes, estimated how many customers each would help, and recommended two. [Vendor claim] https://sierra.ai/blog/ghostwriter-ai-tool-to-teammate
- **Redesign (2 Nov 2026, "Redesigning Agent Studio around Ghostwriter").** Each piece of work is a session: a chat thread holding both the conversation and the changes. Changes stay in the session until someone reviews and merges them. Sessions can be shared, forked and run in parallel. Ghostwriter can review a colleague's changes before merge. The UI offers line-by-line diffs, Preview Chat and Simulations. Projects group related agents with their shared data and channels for joint testing and release. In the lender example, one change to document requirements updates both the document-collection agent and the loan-tracking agent. The redesign replaces Explorer, Sierra Assistant and other specialised helpers. [Fact] https://sierra.ai/blog/redesigning-agent-studio-around-ghostwriter
- **Release governance** (reported by Unite.ai from a Sierra post titled "Release Governance Guardrails for Agents at Scale", which I did not open). Agent Checks is a static analyser that flags issues in journeys and the conversations they produce, ranks them by severity and usually suggests a fix. Organisations can require simulations to pass before production. A Reviewer role names who must approve (CX lead, compliance, engineering manager). Approved releases can go out on split traffic, and every release is an immutable snapshot. [Vendor claim via secondary] https://www.unite.ai/es/sierra-puts-ghostwriter-at-the-center-of-agent-studio-workflows/
- **Performance review (18 Nov 2026).** Customers ShipStation, Carta, Tilt, Airtable and Imprint describe a detect, root-cause, fix-with-tests, follow-up loop. Carta's case: it flagged that the chat agent was failing to create support cases, listed the affected customers and later confirmed recovery. No numbers are given. [Vendor claim] https://sierra.ai/blog/ghostwriters-performance-review
- **Accelerators (5 Nov 2026).** These are prebuilt packages added to an agent: greetings, multilingual handling, name matching, CSAT collection; retail order tracking and returns; banking transaction search, dispute status and lending guardrails; healthcare scheduling, patient authentication and an urgent-call guardrail; telecom retention and billing; insurance quoting and first notice of loss. Unlike templates, they receive updates. Changes are tracked separately from the customer's own edits and reviewed before they are applied. Customer-built Accelerators are planned. [Vendor claim] https://sierra.ai/blog/accelerators

### Sierra Agent Data Platform and memory

Plain English. ADP is the customer's memory across calls. "Hi Maria, last week you asked about the upgrade. Still interested?"

- ADP has two components: a memory layer and a decisioning engine. Memory unifies unstructured data (calls, chats, emails) with structured data (CRM, billing, transactions) and connects to the customer's warehouse or systems of record. The decisioning engine picks the next best offer within a strategy the company defines (audience, desired outcomes, inventory of offers, triggers) and inside guardrails. [Vendor claim] https://sierra.ai/blog/agent-data-platform
- Memory has three levels: explicit saves, builder-configured items, and automatically captured preferences. Recalling sensitive items requires identity verification. Per-customer memory is about three orders of magnitude smaller than the knowledge base. [Vendor claim, secondary] https://www.zenml.io/llmops-database/building-production-scale-voice-and-multi-modal-customer-experience-agents
- Horizon's "context engine" stitches every interaction across parties. In the healthcare referral example that means patient, specialist and referring physician. The agent learns from closed and rejected sales, and the customer owns this context. [Vendor claim] https://sierra.ai/blog/horizon
- No schema, retention or permission details are published. [Unverified]

### Sierra supervisors, monitors and guardrails

- Supervisors run alongside the agent and check each response as it is generated. They verify facts, enforce policy, steer drifting conversations and escalate. [Vendor claim] https://sierra.ai/blog/confidence-in-every-conversation
- Monitors review every conversation after the fact. They are written in natural language, and each flag links to the transcript. Default monitors cover coherence, repetitiveness, grounding and sentiment, and custom monitors can track things like frustration or brand voice. [Vendor claim] same URL
- The stated reliability arithmetic: a 90%-accurate agent paired with a 90%-accurate supervisor reaches about 99% (treating errors as independent). [Vendor claim] https://sierra.ai/blog/meet-the-ai-agent-engineer ; Taylor repeats this. [Fact, transcript]
- Sensitive guardrails can stay fixed while lower-risk tasks change, because capabilities are separated into retrieval, classification, tools, policies and tone. [Vendor claim] https://sierra.ai/blog/constellation-of-models

### Sierra model orchestration ("constellation of models")

- 15+ frontier, open-weight and proprietary models are chosen per task: low-latency tool calling, high-precision classification, long-context policy reasoning, and tone. Sierra runs task-specific evaluations, fine-tunes where needed, adjusts prompts per model family, and keeps redundancy across providers with automatic failover on latency, error-rate and timeout signals. [Vendor claim] https://sierra.ai/blog/constellation-of-models
- About 10 to 15 model calls per conversation turn: a couple of frontier reasoning calls, several classifiers and speculative calls. Knowledge retrieval runs speculatively, and classification runs in parallel with generation. Sierra builds its own retrieval and reranking models. It works with existing model strengths "80% of the time". Prompt compaction must be non-lossy, and prompt caching never outranks quality. [Vendor claim, secondary] https://www.zenml.io/llmops-database/building-production-scale-voice-and-multi-modal-customer-experience-agents

### Sierra voice architecture and voice sims

- Most Sierra conversations are voice. Responses must arrive within about 1 to 2 seconds. Thinking, listening and talking run in parallel, including listening for barge-in. "Progress indicators" are filler lines such as "pulling up your account". Transcription runs two models in parallel and a silence detector picks between them, because the model that handles thick UK accents hallucinates in silence. Speech-to-text, text-to-speech and voice-to-voice providers are multi-homed. Native voice-to-voice handles a small share of traffic: it costs nearly 10x more and its tool calling is weaker. About 60 languages are supported, and Hungarian word error rate reached about 20% on single models. [Vendor claim, secondary] https://www.zenml.io/llmops-database/building-production-scale-voice-and-multi-modal-customer-experience-agents
- Voice sims (23 Sep 2025) use a dual loop. A simulated caller (goal, mood, language, patience, with synthetic voice, background noise and DTMF tones) exchanges audio chunks with the voice loop. An LLM judge grades pass or fail. Tests cover timing (silence, interruptions, overlap) as well as content. Sims run in CI to block bad changes. [Vendor claim] https://sierra.ai/blog/how-voice-sims-work
- Voice Personas (7 Aug 2026) and "Mossy" (9 Nov 2026) are voice-identity posts I did not open. [Unverified]

### Sierra simulations, experiments, traces

- Simulated users vary by language, tech comfort, tone and task. The initial state is set to match production (logged in or not, email on file). The same scenario is run several times, and a separate judge agent grades goal completion, SOP adherence, brand compliance and answer quality. Tests are auto-generated at agent creation from SOPs, knowledge bases, coaching transcripts and flows, and they persist for regression. [Vendor claim] https://sierra.ai/blog/simulations-the-secret-behind-every-great-agent
- Traces: the SDK records the reasoning trace behind each decision, so QA can see why a misbehaviour happened. The Experience Manager lets CX teams annotate daily samples: was the decision right, was the tone right, was knowledge missing, what should the agent have done. [Vendor claim] https://sierra.ai/blog/agent-development-life-cycle
- Experiments: releases can be A/B tested against business goals. Ghostwriter now proposes experiments and reports significance. [Vendor claim] same URL; https://sierra.ai/blog/ghostwriter-ai-tool-to-teammate
- When Sierra upgrades Agent OS, it runs the regression suite for every live customer. [Vendor claim] https://sierra.ai/blog/agent-development-life-cycle

### tau-bench and tau2-bench (Sierra Research)

Plain English. A test where an AI pretends to be a customer ("You are Yusuf Rossi in 19122, exchange the keyboard for a clicky one…"). The agent under test has the shop's tools and a policy document. It passes only if the shop database ends in exactly the right state.

Technical detail, from the code:
- Paper: Yao, Shinn, Razavi and Narasimhan, 17 Jun 2024. Function-calling agents like gpt-4o succeeded on under 50% of tasks, and pass^8 was below 25% in retail. [Fact] https://arxiv.org/abs/2406.12045
- Environment: data loader (the JSON database), a tool list, the policy "wiki" in markdown, rules, and a user simulator. The retail policy requires: authenticate by email or by name plus zip even when the user gives an ID; one user per conversation; list action details and get an explicit "yes" before any write; no invented information; one tool call at a time; transfer to a human only when out of scope. [Fact] /home/claude/research/_code/tau-bench/tau_bench/envs/retail/wiki.md ; rules.py
- Reward: hash the final database. Reset, replay the task's reference actions, and hash again. Reward is 1 only if the hashes match and every required output string appears in the agent's replies. [Fact] /home/claude/research/_code/tau-bench/tau_bench/envs/base.py
- In tau2, reward is the product of the components in `reward_basis` (default DB × COMMUNICATE). The reference actions are only one valid path: any trajectory reaching an equivalent end state passes. ACTION-matching is used only in a few banking_knowledge tasks. Other components are env_assertions and nl_assertions judged by an LLM. [Fact] /home/claude/research/_code/tau2-bench/docs/evaluation.md
- pass^k = comb(successes, k) / comb(trials, k). [Fact] /home/claude/research/_code/tau2-bench/src/tau2/metrics/agent_metrics.py
- "Dual control": in the telecom domain the simulated user has its own tools (check status bar, toggle airplane mode, run a speed test), so the agent must guide the user to act. [Fact] /home/claude/research/_code/tau2-bench/src/tau2/domains/telecom/user_tools.py ; paper https://arxiv.org/pdf/2506.07982
- tau-bench 2.0 adds six languages, full-duplex voice, an `intake` domain for exact entity capture (200+ tasks), banking_knowledge (retrieval) and post-hoc speech judges. Benchmarks are frozen at 50 tasks per domain per language. The default semantic judge is gpt-5.5. [Fact] /home/claude/research/_code/tau2-bench/README.md

### Sierra outcome-based pricing and what a "resolution" is

- Definition (10 Dec 2024). Pricing tracks business impact: a resolved conversation, a saved cancellation, an upsell, a cross-sell. "If the conversation is unresolved, in most cases, there's no charge." Escalations are generally not charged. Sierra and the customer agree outcome criteria up front. Where outcomes do not fit, Sierra blends in per-conversation billing (for example routing or greeter flows). [Vendor claim] https://sierra.ai/blog/outcome-based-pricing-for-ai-agents
- Taylor's operational definition: if the agent solves the problem, the customer is happy, and nobody had to pick up the phone, "there's a pre-negotiated rate". He cites a human call cost of $10 to $20. Some sales agents are paid a commission. [Fact, transcript] https://raw.githubusercontent.com/ChatPRD/lennys-podcast-transcripts/main/episodes/bret-taylor/transcript.md
- "Outcomemaxxing" (3 Jun 2026). Outcome pricing needs high autonomy and clean attribution; without them you get "an endless debate". It has real contractual and accounting complexity. It reorganises sales, product and support around delivering the result. Outcomes do not shrink as token prices fall. [Vendor claim] https://sierra.ai/blog/outcomemaxxing
- Horizon and the 30 Oct 2026 post: pay "for outcomes, not tokens used", with Sierra carrying token-cost risk. Examples: a refinanced loan, a paid claim, a closed sale, a retained customer. [Vendor claim] https://sierra.ai/blog/horizon ; https://sierra.ai/blog/our-customers-ambition-is-accelerating-our-growth
- Sacra: routine traffic tends to be volume-priced, complex work outcome-priced, the blend set per client, no public rates. [Analyst] https://www.sacra.com/c/sierra

### Harvey: review tables and the review algorithm

- The review table is a grid: rows are documents, columns are questions. A cell holds the answer, the reasoning and citations, and rows can be assigned, verified or locked. [Fact] https://www.harvey.ai/blog/making-review-tables-faster-and-more-reliable
- Algorithm rebuild (21 Apr 2026). The output changed from summary plus context to answer plus reasoning, and citations moved from cell-level to sentence-level indices. Attorney side-by-side tests showed 4x overall preference and 7x on credit agreements and trial exhibits. A 30-column, 1,000-document table means 30,000 concurrent cells. The evaluation datasets were built by internal legal researchers, and nobody sees real customer queries. [Vendor claim] https://www.harvey.ai/blog/rebuilding-harveys-review-algorithm
- Storage rebuild (22 Oct 2026). Postgres holds metadata and is the source of truth. Raw customer data lives in segregated Azure blobs. Turbopuffer is the read path (CQRS). Paging is ID-based (the backend returns ordered row IDs and the client fetches rows by ID). Non-string LLM outputs are stored twice, typed and as a string. If drift is detected, reads fall back to Postgres and a backfill repairs the index. Speedups range from 1.2x (under 1K cells) to 5.8x (10K to 100K cells). [Fact] same URL

### Harvey: playbooks, the most direct "company rules" capture

- Each playbook rule holds a standard position, acceptable deviations (fallbacks), unacceptable deviations (dealbreakers), guidance, and an "optional" flag. Shared context: represented party, whose paper, negotiation strictness, deal instructions, precedents. [Fact] https://www.harvey.ai/blog/rebuilding-playbook-review-as-a-multi-agent-system
- Architecture (2 Sep 2026). An orchestrator spawns one subagent per rule, up to dozens in parallel. Each subagent classifies compliance, picks a position and drafts edits on its own branch of a versioned document model where every component has an ID. Edits are tracked changes tagged with the rule that produced them. Branches merge like version control, and collisions go to the orchestrator. A final validation pass confirms every rule was classified. Results: risk classification 59% to 77%, redline rubric 53% to 87%, latency 2.6 to 3.8 minutes. Redlines were judged by a committee of three frontier models. Engineering: per-phase timeouts, retrying only the failed rules, concurrency caps, prompts ordered for prefix-cache hits, streaming per rule, per-phase model choice. [Fact] same URL

### Harvey: ethical walls (permission model)

Plain English. A law firm may act for Company A while other lawyers in the firm must not see A's documents (a conflict). The wall says who can or cannot see a matter. Harvey must apply it everywhere: search, chat, agents, sharing and memory.

- Data model: Client Matter (open or walled), Wall (inclusionary or exclusionary), and membership sets stored once per workspace. Each set is fingerprinted by a hash of the normalised member list, is never edited in place, and a changed wall is repointed to a new set. Resource links connect Vault projects and files, conversations, review tables and Spaces to matters, and a file can carry its own matter link. [Fact] https://www.harvey.ai/blog/building-ethical-wall-enforcement-into-harvey
- Sync: separate matter-sync and wall-sync jobs on Temporal, with schedules, bulk runs and on-demand refresh, plus webhooks where available. Failures keep the last known policy. Users are matched by email, and an unmatched person on an inclusionary wall stays excluded. The largest workspace has about 1.7M matters. [Fact] same URL
- Enforcement: one policy engine. Access needs the resource permission plus clearance for every linked matter. A conversation inherits the matters of every attached file and every Vault source, and keeps them after a file is removed. Retrieval filters the index before ranking, then re-checks each file against stored policy before any content goes to the model. Scheduled agents run as their creator and check each file. Matter-tied memories check the wall. Shares are checked on share and again on open. Unauthorised items respond as if they do not exist. No admin bypass. Audit events cover wall create, change and remove, exportable by API. [Fact] same URL. iManage wall extension post (29 Oct 2026) not opened. [Unverified]

### Harvey: connectors and the MCP policy engine

- Each connector is a vendor-level catalogue object with one permission and an admin toggle. Its members are native API wrappers or vendor MCP servers. A code-resident registry defines identity, capabilities, permission and routing notes. Resolution happens once per turn. Every call uses the user's own credential, so the source system's ACLs apply. Effective MCP tools = vendor-advertised ∩ Harvey-reviewed ∩ workspace and user settings ∩ the user's selection. Scale: 110,000+ connections, tens of thousands of tool calls a week, about 13M credential reads a day. OAuth 2.1 with PKCE plus RFC 9728/8414/7591/8707, with adapters for vendor deviations (for example, tokens returned with 201). Single-use refresh tokens are handled with conditional write-backs rather than locks. [Fact] https://www.harvey.ai/blog/how-we-built-harvey-connector-library
- Policy engine: Rego (Regorus/OPA in-process). The engine is data-blind and fails closed. Decisions are allow, deny or pause for approval. Argument risk is scored on capacity (how much data an argument can carry) and authority (what it controls). It detects delegation cycles. A Tool Pinner flags changes to descriptions and schemas (it produces many alerts). A sanitizer strips hidden characters and confusables. Telemetry excludes arguments and results. [Fact] https://www.harvey.ai/blog/building-harveys-mcp-policy-engine

## Cross-cutting patterns

(a) **How the successful ones capture procedures and rules**
- One artifact holds three layers. (1) A natural-language procedure for the flow (journey, AOP, Procedure, playbook rule). (2) Deterministic checks for hard rules, as code blocks or guardrails (Sierra's 30-day window; Fin's eligibility and date maths). (3) Typed tools from a connector library that carry the user's or service's credentials. [Fact] Sierra, Decagon, Fin URLs above
- Harvey's playbook schema is the cleanest structured rule format published: standard position, acceptable fallbacks, dealbreakers, guidance, optional flag, plus deal context. [Fact] https://www.harvey.ai/blog/rebuilding-playbook-review-as-a-multi-agent-system
- Capture is now automated from existing artifacts: SOP PDFs, transcripts, tickets, recordings (Sierra's Ghostwriter, Decagon's transcript-to-AOP), and Ramp's policy PDF plus historical approvals including exceptions. A human still reviews the draft. [Vendor claim]
- Facts go into a source-linked, versioned graph at ingestion (Hebbia, Distyl), with entity resolution and effective dates. [Vendor claim]

(b) **How they test before release**
- Simulated user plus mocked tools plus end-state check (tau-bench pattern), run k times to get pass^k. [Fact]
- Tests are auto-generated from SOPs and knowledge, and every production failure becomes a regression test. Tests run from CI or a CLI and gate releases. [Vendor claim] Sierra
- Before human review: static checks on the procedure (Sierra's Agent Checks), then simulations, then named reviewers, then split traffic. [Vendor claim, secondary]
- Rubrics are atomic and binary, scoped to deliverables, judged by two or three different LLM judges (Harvey LAB; the playbook redline committee). [Fact]
- Every vendor runs always-on post-release monitors over 100% of conversations. [Vendor claim]

(c) **How they price**
- Customer service: per resolution or outcome, with per-conversation billing for non-attributable traffic (Sierra, Decagon, Fin $0.99). Definitions are agreed up front (Sierra) or published (Fin: no further help requested after the last answer, once per conversation). [Fact/Vendor claim]
- Professional work: seats at a high price ($1,200 per lawyer per month) plus custom fees (Harvey). [Analyst]
- Platforms and SMB: credits or usage (Lindy, Tencent ADP). [Fact]
- Failure mode: annual contracts with break clauses counted as ARR (11x). [Fact, reporting]

(d) **How they deploy quickly**
- Paired roles: an agent PM (business, requirements, executive) and an agent or deployment engineer (build, tools, tests). [Fact] Sierra and Decagon job posts and blogs
- Packaged, updatable starting points (Sierra Accelerators), with customer-specific edits tracked separately so vendor updates can be reviewed and merged. [Vendor claim]
- A connector library flow (pick, credentials, publish) that exposes tools to both no-code and code. [Vendor claim]
- Start on a small slice of traffic and a few intents, security-test misuse, then widen (WeightWatchers). [Vendor claim]
- Reported time to live: 27 days to 10 weeks for large enterprises. [Vendor claim]

(e) **How they expand from the first job**
- Support answers, then authenticated actions (returns, payments), then memory and personalisation (ADP), then revenue (offers, retention, sales commission), then long-horizon outbound and inbound outcomes (Horizon, Missions). [Vendor claim]
- In legal: chat, then Vault document grids, then workflows and playbooks, then cloud agents across whole data rooms, then admin analytics (Command Center), which shows where to expand next. [Vendor claim]
- Expansion inside an account is measured in seats or intents (Harvey's median seats double within 12 months). [Analyst]

## Which jobs are proven and which have visibly failed (2025 to 2026)

Proven (evidence of production scale and repeat buying):
- **Tier-1 customer service with authenticated actions** (returns, order status, billing, subscription changes, troubleshooting). Fin reports 76% average resolution across 12,000+ customers; Sierra customers report 70 to 80% resolution (Chime, Airtable, WeightWatchers); Sierra reached $400M+ ARR and Decagon about $100M. [Vendor claim/Analyst]
- **Document review and extraction at scale in legal and finance** (review tables, playbook redlines, diligence). Harvey reports 700K+ tasks a day and 50M+ terms extracted a week, with $400M+ ARR (analyst estimate); Hebbia's Matrix serves funds and banks. [Vendor claim/Analyst]
- **Ambient clinical documentation.** Abridge reports 300+ health systems and 53M+ conversations a year. [Vendor claim]
- **Expense-policy enforcement.** Ramp claims 99% accuracy with 10 to 15% escalated. [Vendor claim]
- **Voice customer service.** Most Sierra conversations are voice, with a supporting stack of ensembled transcription and fillers. [Vendor claim, secondary]

Visibly failed or weak:
- **Autonomous outbound SDRs (sales development reps).** 11x: churn, ARR inflation and hallucinations. [Fact, reporting]
- **Generic enterprise pilots.** Sierra itself cites an MIT study saying 95% of AI pilots fail to show returns. [Vendor citation] https://sierra.ai/blog/year-two-in-review
- **Proprietary vertical models.** Harvey reportedly dropped its own legal model when frontier models beat it. [Analyst] https://sacra.com/c/harvey/
- **Rule-chained prompt pipelines for complex review.** Harvey's playbook pipeline lost context and produced conflicting edits until rebuilt as orchestrator plus subagents. [Fact]
- **Retrieval-only agents on table-heavy numeric questions.** Search agents scored 26 to 39% on OfficeQA because they misread rows and units after retrieval. [Vendor claim] Distyl
- Customer-service reversals (for example companies re-adding human agents after AI-first announcements) are widely reported, but I could not open sources this session. [Unverified]

## What to copy

1. **Procedure object = natural-language steps + deterministic guard code + allowed tools, versioned in Git.** Store each procedure as a document with typed blocks (`step`, `if/else`, `code_check`, `tool_call(ref)`, `escalate_when`). Compile it to an executable form deterministically, so no-code and code edit one artifact. Why: Sierra, Decagon and Fin all converged here, and Sierra round-trips journeys to SDK code. Sources: https://sierra.ai/blog/agent-studio-2-0 ; https://www.zenml.io/llmops-database/building-production-scale-voice-and-multi-modal-customer-experience-agents ; https://fin.ai/procedures ; https://decagon.ai/product/aop
2. **Hard business rules live as deterministic guards outside the LLM.** For example, `refund.allowed = order.delivered_at > now()-30d`. Evaluate the guard before any write tool executes; the LLM cannot override it. Source: https://sierra.ai/blog/agent-development-life-cycle
3. **Immutable release snapshot.** Bundle procedure code, prompts, model IDs and versions, connector and tool schemas, and a frozen copy of the knowledge index. Promote QA, then staging, then production; one-click rollback; split-traffic releases. Source: https://sierra.ai/blog/agent-development-life-cycle ; https://sierra.ai/blog/agent-studio-2-0
4. **Sessions as branches.** Every change (human or agent) goes in a session holding chat plus diff. Sessions can be shared and forked and run in parallel. Merging requires named reviewer roles, and policy can require passing simulations first. Source: https://sierra.ai/blog/redesigning-agent-studio-around-ghostwriter ; https://www.unite.ai/es/sierra-puts-ghostwriter-at-the-center-of-agent-studio-workflows/
5. **tau-bench-style evaluation harness.** Each test = user instruction + initial DB snapshot + reference action list + required communicated facts + optional NL assertions. Reward = DB end-state hash equality × communicate check. Report pass^k = C(s,k)/C(n,k) with k ≥ 4. Mock every connector from the same tool schemas. Source: /home/claude/research/_code/tau2-bench/docs/evaluation.md ; https://arxiv.org/abs/2406.12045
6. **Simulate users who have their own tools when the customer must act** (dual control, for example "toggle airplane mode"). Source: https://arxiv.org/pdf/2506.07982
7. **Failure-to-test pipeline.** One click converts an annotated bad conversation into a simulation with mocked APIs. Auto-generate initial tests from the SOPs. Expose a CLI and GitHub Action to gate releases. Source: https://sierra.ai/blog/simulations-the-secret-behind-every-great-agent
8. **Atomic binary rubric criteria scoped to deliverables, judged by two different models, all-pass scoring** for report and document outputs from internal agents. Source: /home/claude/research/_code/harvey-labs/docs/eval-strategies.md
9. **Improvement agent with mandatory human merge.** Detect from 100% of traffic, then root-cause, then draft a change on a branch, then test against the originating case plus a golden set, then notify only when ready, then a human approves. Let admins declare off-limits procedures. Source: https://decagon.ai/blog/autopilot ; https://sierra.ai/blog/ghostwriters-performance-review
10. **Natural-language monitors over every conversation** (defaults: coherence, repetition, grounding, sentiment), each flag linked to its trace, plus an in-line supervisor model checking each response before it is sent. Source: https://sierra.ai/blog/confidence-in-every-conversation
11. **Permission model copied from Harvey's ethical walls.** Resources link to scopes (matters, clients, departments). Policies are inclusionary or exclusionary. Membership sets are immutable and content-hashed. The search index holds no policy data and is filtered before ranking. Each item is re-checked against stored policy before content reaches the model. Agents run as their creator. Derived artifacts inherit the scopes of all their sources and keep them. Unauthorised items look nonexistent. No admin bypass. Audit events are exportable. Source: https://www.harvey.ai/blog/building-ethical-wall-enforcement-into-harvey
12. **Tool-call policy engine.** Embed OPA/Rego in-process. Inputs are tool ID, your own risk annotation (capacity, authority), capability flags and prior call names only. Outputs are allow, deny or require approval. Fail closed. Pin tool descriptions and schemas and alert on drift. Sanitise tool results for hidden characters. Effective tools = advertised ∩ reviewed ∩ admin ∩ user ∩ selected. Source: https://www.harvey.ai/blog/building-harveys-mcp-policy-engine ; https://www.harvey.ai/blog/how-we-built-harvey-connector-library
13. **Per-user credentials on every connector call**, so source-system ACLs apply. Resolve the tool set once per turn. Use conditional write-backs for single-use refresh tokens. Source: https://www.harvey.ai/blog/how-we-built-harvey-connector-library
14. **Source-linked fact graph built at ingestion.** Each fact = normalised value + entity + source doc and location + effective date + version. Run alias resolution that refuses to merge look-alikes. Apply permissions per entity and relationship. When access limits an answer, say so. Source: https://www.hebbia.com/blog/building-a-knowledge-graph-for-financial-institutions ; https://www.distyl.ai/blog/research/context-views-what-a-knowledge-graph-buys-an-agent
15. **Durable ingestion.** Use a workflow engine (Temporal or similar) with per-activity timeouts and retries, isolate per-file failures, version the intermediate document format with typed components, use an OCR fallback chain, and run region-pinned workers. Source: https://www.harvey.ai/blog/scaling-document-processing-across-harvey
16. **Grid ("review table") as the bulk-analysis object.** Rows are entities or documents, columns are questions, and each cell holds answer + reasoning + sentence-level citations + verify/lock state. Postgres is the truth store with a separate read index. Store typed values twice (typed and string). Fall back to Postgres on drift. Source: https://www.harvey.ai/blog/making-review-tables-faster-and-more-reliable ; https://www.harvey.ai/blog/rebuilding-harveys-review-algorithm
17. **Rule-structured policy objects** (standard / acceptable / unacceptable / guidance / optional), reviewed by an orchestrator with one subagent per rule. Each subagent edits on its own branch of an ID-addressed document, and edits are tagged with the rule that made them. Source: https://www.harvey.ai/blog/rebuilding-playbook-review-as-a-multi-agent-system
18. **Model router.** Task classes (fast tool call, classifier, long-context reasoning, tone). For each class keep a ranked list of equivalent models across providers, with health checks on latency, errors and timeouts and automatic failover. Route to the cheapest model that passes the class's eval threshold. Source: https://sierra.ai/blog/constellation-of-models ; https://www.harvey.ai/blog/why-we-built-our-own-cloud-agent-infrastructure
19. **Zero-data-retention runtime.** Session-scoped agent state and transient sandbox disks purged at teardown. Source: https://www.harvey.ai/blog/why-we-built-our-own-cloud-agent-infrastructure
20. **Cache-friendly context.** Stable prompt prefixes, append-only context, deterministic serialisation, tool masking instead of removal, file-system memory, a todo-list recitation, errors kept in context. Track KV-cache hit rate as a top metric. Source: https://manus.im/blog/Context-Engineering-for-AI-Agents-Lessons-from-Building-Manus
21. **Policy capture from existing artifacts.** Ingest the policy PDF plus historical decisions including exceptions, draft the rule set, and have a human confirm. Every agent decision stores a rationale and feeds back. Autonomy goes from recommend to decide per rule. Source: https://ramp.com/blog/ramp-agents-announcement
22. **Updatable packages (Accelerators)** for common procedures. Customer edits are tracked separately from the package so vendor updates arrive as reviewable merges. Source: https://sierra.ai/blog/accelerators
23. **Outcome metering.** Log an `outcome` event per conversation using a definition agreed per customer and stored in the contract config (Fin's version: no further help requested after the last answer, at most once per conversation; escalations free). Bill non-attributable traffic per conversation. Source: https://fin.ai/pricing ; https://sierra.ai/blog/outcome-based-pricing-for-ai-agents
24. **Approval gate for external effects.** Writes, sends and publishes need approval until the rule is promoted; read-only lookups do not. Source: https://www.lindy.ai/pricing ; https://www.harvey.ai/blog/building-harveys-mcp-policy-engine
25. **Usage analytics agent for admins** (Command Center): usage by department, peer benchmarks and recommendations for what to enable next. This drives expansion. Source: https://www.harvey.ai/blog/introducing-command-center

## What cannot or should not be copied

- **Proprietary models** (Fin Apex, fin-cx-retrieval and reranker; Sierra's in-house retrieval and reranking models and fine-tunes; Harvey Tenet; Decagon's voice models). The brief rules out training. Use third-party rerankers and embeddings instead. [Inference]
- **Native voice at Sierra's level** (ensembled transcription, ~60 languages, full-duplex sims). This is a large specialised investment. A solo founder should start text-first or buy a voice platform. [Inference]
- **The forward-deployed staffing model at scale.** Sierra and Decagon pair a PM and an engineer per account and charge enterprise prices. A solo founder with 100 to 1,000-staff customers cannot staff that. Replace people with packaged procedures and an improvement agent, but expect some services work. [Inference]
- **Pure outcome pricing at the start.** It needs autonomy, attribution and contractual and accounting maturity ("not simple"). For internal agents (reports, answers), outcomes are hard to attribute. Start with seats or usage plus an outcome option for clearly attributable external jobs. [Inference based on https://sierra.ai/blog/outcomemaxxing]
- **Harvey's legal-specific objects** (matters, ethical walls) as named. Copy the mechanics, but generalise "matter" to any scope object. [Inference]
- **Peer benchmarking across 1,500 deployments.** It needs a customer base you do not yet have. [Inference]
- **Vendor-reported results as targets.** Most numbers here are self-reported, measured inconsistently, and cover the vendor's best customers. [Inference]
- **The 11x pattern**: break-clause contracts counted as ARR, and logos from trials. [Fact, reporting]
