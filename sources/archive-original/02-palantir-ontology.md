# The Palantir Ontology, bolt by bolt

Scope note (written 21 November 2026). This document takes the Palantir Foundry Ontology apart component by component, for a founder who wants to copy its design into a smaller "company model for AI agents" product. It covers the type system (object types, properties, links, interfaces, value types), the query model (object sets), the write model (action types, functions, edits), the backend services (Ontology Metadata Service, Object Set Service, Object Storage v1 and v2, Funnel indexing, materializations), permissions, the developer surface (OSDK, Developer Console, Platform API, Ontology MCP), cost and scale numbers, and Palantir's own modelling guidance. Sources are the Palantir Foundry documentation (read page by page on 21 November 2026; pages carry no visible publication dates, so "as documented on 21 Nov 2026" is the date for every doc claim) and two open-source Palantir repositories cloned on the same day: `palantir/osdk-ts` (commit 09b6f4f, 20 Nov 2026) and `palantir/foundry-platform-python` (commit b84ce26, 20 Nov 2026). The repositories expose internal API shapes (including generated types for the internal Ontology Metadata Service and Object Set Service) that the docs only describe in prose. Partway through, the shared web-fetch and search budget ran out, so several sub-pages could not be opened; those gaps are listed in "Open questions".

Labels: [Fact] = stated in the cited primary source. [Vendor claim] = a Palantir assertion of benefit that is not independently measurable. [Inference] = my reasoning. [Unverified] = I could not find or open a source.

## Key findings

1. **The Ontology is metadata plus an index, not a database of record.** Object types are schemas mapped onto existing datasources (datasets, restricted views, streams). A pipeline called Funnel copies source rows and user edits into a purpose-built search index (Object Storage v2), and every read goes through a separate query service (Object Set Service). User edits are stored as an overlay keyed by primary key and merged with source rows on a schedule. [Fact] https://www.palantir.com/docs/foundry/object-backend/overview , https://www.palantir.com/docs/foundry/object-indexing/funnel-batch-pipelines/
2. **Writes go only through typed, governed "action types".** OSv2 accepts user edits only via actions [Fact] (https://www.palantir.com/docs/foundry/object-backend/object-storage-v2-breaking-changes/). An action type is a declarative bundle of typed parameters, rules that map parameters to edits, submission criteria (who, and under what data conditions), and side effects (notifications, webhooks). This is the single most copyable idea for an agent product: agents never write raw rows; they call named business operations that validate and log themselves.
3. **Edits are atomic, snapshot-isolated, and retried.** Ontology edits in one action commit all-or-nothing; the default isolation for new actions is snapshot isolation with object-level conflict detection; transient failures retry up to 5 times, but by default only for actions without external calls. Webhooks and notifications are outside the atomic boundary. [Fact] https://www.palantir.com/docs/foundry/action-types/consistency-guarantees/
4. **Two webhook modes encode the hard part of writeback.** A "writeback" webhook runs before edits and blocks them if it fails (at most one per action); "side-effect" webhooks run after edits, best-effort, unordered, failures hidden from the user. Palantir is explicit that the external call can succeed while the Ontology commit then fails. [Fact] https://www.palantir.com/docs/foundry/action-types/webhooks/
5. **Every decision is logged as an object.** The action log turns each successful submission into an object of a generated `[Log] <action>` type with action RID, version, timestamp, user, edited object keys, webhook and notification IDs, scenario, revert status and optional parameter values, linked to every edited object. Separately, edit history tracks every direct edit per object. [Fact] https://www.palantir.com/docs/foundry/action-types/action-log/ , https://www.palantir.com/docs/foundry/object-edits/user-edit-history/
6. **User edits win over source data by default, with a per-datasource opt-in for "most recent wins".** Default: an edited property ignores later source updates forever; unedited properties follow the source. Alternative (OSv2 only): compare a UTC timestamp column in the source to the edit time, per property. Deletes are sticky and recreated objects do not inherit old edits. [Fact] https://www.palantir.com/docs/foundry/object-edits/how-edits-applied/
7. **The query model is a composable algebra of object sets.** Base set, filter, union, intersect, subtract, search-around (follow a link), nearest-neighbours, interface casts, and runtime derived properties (`withProperties`), then page, aggregate or subscribe. The same tree is the wire format in the REST API. [Fact] `foundry-platform-python/foundry_sdk/v2/ontologies/models.py` (`ObjectSet` union), `osdk-ts/packages/api/src/objectSet/ObjectSet.ts`
8. **Hard scale limits are published and are smaller than people assume.** Per action: 10,000 objects edited, 50 object types, 3 MB per object edit (OSv2). Batch: 10,000 calls, but only 20 for function-backed actions without batched execution. Search-around: in-memory up to 100,000 objects, Spark fallback beyond, 10 million leaf cap, 30 million total per query. Max 2,000 properties per object type (OSv2), 250 for streaming types, 70 backing datasources per type. [Fact] https://www.palantir.com/docs/foundry/action-types/scale-property-limits/ , https://www.palantir.com/docs/foundry/ontologies/oss-limitations/ , https://www.palantir.com/docs/foundry/object-permissioning/multi-datasource-objects/
9. **Security is evaluated at read time, at row, column and cell level, and is separate for metadata and data.** Seeing an object type's schema and seeing its objects are different permissions. Object security policies (row), property security policies (column) and mandatory control properties (per-row markings) combine into cell-level security; failing a property policy yields `null`, failing the object policy hides the object. Policies do not follow data into exports. [Fact] https://www.palantir.com/docs/foundry/object-permissioning/object-security-policies/ , https://www.palantir.com/docs/foundry/object-link-types/mandatory-control-properties/
10. **Agent access is the intersection of three things.** A token's effective scope = the user's own permissions ∩ the application's maximum resource and operation restrictions ∩ the operation scope requested. A token requested with no scope restriction gets no permissions. [Fact] https://www.palantir.com/docs/foundry/developer-console/application-restrictions/
11. **Ontology MCP exposes the same governed surface to external agents.** Each action type becomes its own tool, each selected query function its own tool, and object types are reachable through a single SQL tool; auth reuses the Developer Console app's OAuth client (authorization code for per-user agents, client credentials for service agents). The builder can write an "agent tool description" per action. [Fact] https://www.palantir.com/docs/foundry/ontology-mcp/sample-architecture/ , https://www.palantir.com/docs/foundry/ontology-mcp/authentication-and-authorization/ , https://www.palantir.com/docs/foundry/ontology-mcp/mcp-tools-and-agent-configuration/
12. **Pricing exposes the cost model.** From 1 January 2026 every query has a minimum charge: 2 compute-seconds for a base query, 5 for a search-around, aggregation or SQL query, 10 for semantic search or derived-property queries, 18 for an action plus 1 per extra edited object. Indexing is Spark compute; storage is the uncompressed index size in GB-months. [Fact] https://palantir.com/docs/foundry/ontologies/query-compute-usage/ , https://palantir.com/docs/foundry/ontologies/compute-usage/ , https://palantir.com/docs/foundry/ontologies/volume-usage/
13. **Ontology changes have a lifecycle: statuses, branches, proposals, schema migrations.** Resources are experimental, active, deprecated (with deletion deadline), example, or promoted; active resources cannot be deleted or have API names changed. Changes can be made on a branch, reviewed in a proposal, rebased, and merged. Breaking schema changes on types with edits require an explicit migration (drop, move, cast, backfill). [Fact] https://www.palantir.com/docs/foundry/object-link-types/metadata-statuses/ , https://palantir.com/docs/foundry/ontologies/branching-ontology/ , https://www.palantir.com/docs/foundry/object-edits/schema-migrations/
14. **Palantir's own modelling guidance is now written with agents in mind.** Its validation method tests an ontology by running real business questions through people and then through an AI agent without path hints, and reads the difference as a diagnosis (for example, people succeed but AI fails = business knowledge not encoded). [Fact] https://palantir.com/docs/foundry/ontology/ontology-design-validation/
15. **OSv1 (Phonograph) is end of life.** It is scheduled to be unavailable after 30 June 2026 [Fact] (https://www.palantir.com/docs/foundry/object-backend/overview). As of 21 November 2026 that date has passed; I could not confirm whether the shutdown happened on schedule [Unverified]. Copy OSv2 behaviour only.

## Breakdown

### 1. How Palantir frames the Ontology (data, logic, action, security; semantic vs kinetic)

Plain English: the Ontology is a map of the business written in business words (customers, orders, aircraft), connected to the real data, with the allowed ways of changing things attached. Example: "Flight" is linked to "Aircraft"; a "Reassign aircraft" action changes the link and notifies the controller.

Technical detail:
- Palantir splits the Ontology into **semantic** elements (objects, properties, links: what things are) and **kinetic** elements (action types, functions, and dynamic security: how things change), plus **interfaces** for polymorphism. [Fact] https://www.palantir.com/docs/foundry/ontology/overview/
- The "Why create an Ontology?" page argues the model should capture **decisions**, not just data, and breaks a decision into four parts: data (including "decision data": context, options considered, effects), logic (rules, forecasts, optimisers, LLM functions, bound through one interface), action ("verbs" to data's "nouns", stageable as scenarios, written back to source systems), and security (marking, purpose and role policies computed per interaction; agent tool use tied to access to the underlying objects). [Vendor claim] https://palantir.com/docs/foundry/ontology/why-ontology/
- The Architecture Center describes three layers: a **Language** (definitions of objects, links, actions, automations, logic), an **Engine** (read path: high-scale queries, real-time subscriptions, materializations; write path: atomic transactional updates, batch mutations, streams, change data capture to operational systems), and a **Toolchain** (OSDK and DevOps tooling). It states the Ontology is not merely a semantic layer. [Vendor claim] https://palantir.com/docs/foundry/architecture-center/ontology-system/
- Core vocabulary: object type (schema), object (instance), object set (collection); property and property value; shared property; link type and link; action type and action; roles; functions; interfaces; object views. [Fact] https://www.palantir.com/docs/foundry/ontology/core-concepts/
- Type system: "Ontology types" model the domain; "data types" are modelled on RDF, OWL and XSD datatype concepts. Field types and base types are fixed; users can create value types. [Fact] https://www.palantir.com/docs/foundry/object-link-types/type-reference/

[Inference] For the founder, the useful framing is: semantic layer (types) + governed write layer (actions) + logic layer (functions) + security evaluated on every call, with every write producing a decision record. The "decision data" idea maps directly onto the action log (section 10).

### 2. Object types

Plain English: an object type is a table definition in business terms. "Employee" with properties name, start date, manager. Each row of the backing data becomes one object, identified by its primary key.

Technical detail:
- **Backing datasources.** An object type maps columns of a datasource to properties. Analogy given by Palantir: object type ≈ dataset, object ≈ row, object set ≈ filtered rows. An object type can have no datasource if all objects are created by actions. [Fact] https://www.palantir.com/docs/foundry/object-link-types/object-types-overview/
- A datasource can back only one object type (error `Phonograph2:DatasetAndBranchAlreadyRegistered`). Backing datasets cannot contain `MapType` or `StructType` columns in the create wizard (struct properties are added from struct columns separately). Without a datasource you must save the type in a project, configure an object security policy, still define a primary key, and populate everything through actions; an empty dataset is created to carry permissions. [Fact] https://www.palantir.com/docs/foundry/object-link-types/create-object-type/
- The ontology-as-code package lists the datasource kinds a type can use: `dataset`, `stream`, `restrictedView`, `derived` (link-based derived properties), and `direct`. [Fact] `osdk-ts/packages/maker/src/api/object/ObjectTypeDatasourceDefinition.ts`. The internal OMS types list more, including time series, media, media set view, geotime series, table (Iceberg-style), restricted stream and `editsOnly`. [Fact] `osdk-ts/packages/client.unstable/src/generated/ontology-metadata/api/__components.ts`
- **Primary key.** Must be unique per row and deterministic (derived from columns, never row numbers or random values), because edits and links attach to primary key values; changing the key prompts you to delete edits. Duplicates fail the OSv2 index build; on OSv1 they silently corrupted state. [Fact] https://www.palantir.com/docs/foundry/object-link-types/create-object-type/ . Valid key types: String, Integer, Short; Date, Timestamp, Boolean, Byte, Long are "discouraged" (format collisions, Boolean allows only two objects, Long loses JavaScript precision above 1e15); floats, decimals, arrays, structs, vectors, geo, media, attachments, markings, cipher are invalid. [Fact] https://www.palantir.com/docs/foundry/object-link-types/properties-overview/
- **Title key.** The display name property; need not be unique. [Fact] https://www.palantir.com/docs/foundry/object-link-types/create-object-type/
- **Naming rules.** Object type API name: PascalCase, alphanumeric, unique, 1-100 characters. Property API name: camelCase, unique within the type, 1-100 characters. Reserved words include `ontology`, `object`, `property`, `link`, `relation`, `rid`, `primaryKey`, `typeId`, `ontologyObject`. Object type ID: lowercase letters, numbers, dashes; changing it breaks applications. [Fact] same page.
- **Metadata fields.** ID, RID (platform-wide resource ID), icon (glyph and colour), display name, plural display name, description, groups (multi-valued labels), API name, visibility (`prominent`, `normal`, `hidden`), status, index status (`success`, `failed`, `not started`), writeback (dataset generated or not; editing enabled or not). [Fact] https://www.palantir.com/docs/foundry/object-link-types/object-type-metadata/ . The code-level definition adds `aliases`, `implementsInterfaces`, `editsEnabled`, `editsHistoryConfig`, `interfaceActionsEnabled`, `permission`. [Fact] `osdk-ts/packages/maker/src/api/object/ObjectTypeDefinition.ts`
- **Statuses** apply to object types, properties, link types, action types and interfaces: `experimental` (default), `active` (no major breaking changes; cannot be deleted; API name frozen), `deprecated` (requires a reason, a deletion deadline, optional replacement), `example`. Object types alone can be **promoted** (internally `endorsed`), applied only by Ontology Owners or via proposal, and it forces prominent visibility. Status propagates: an experimental object type forces its link types to be experimental; a link's status must not conflict with its foreign key property's status. [Fact] https://www.palantir.com/docs/foundry/object-link-types/metadata-statuses/ ; `ObjectTypeStatus_endorsed` in `__components.ts`.
- **Multi-datasource object types (MDOs).** One object type can join up to 70 datasources (datasets or restricted views, not streams) on the primary key, column-wise only (no row-wise union). Each property comes from exactly one datasource. A user who lacks access to one datasource sees its properties as `null`; rows missing from one datasource show `null` rather than being dropped. MDOs are the mechanism for column-level permissions in OSv2. Palantir notes that filtering on one type's properties is cheaper than traversing links, which is the trade-off against splitting into linked types. [Fact] https://www.palantir.com/docs/foundry/object-permissioning/multi-datasource-objects/

### 3. Properties and property types

Plain English: a property is a column with meaning. "startDate" on Employee is a Date; "location" on Plant is a Geopoint; "embedding" on Document is a Vector used for semantic search.

Technical detail:
- **Base types** (complete list from the properties table): String, Integer, Short, Date, Timestamp, Boolean, Byte, Long, Float, Double, Decimal, Vector, Array, Struct, Media Reference, Time Series, Geotemporal Series, Attachment, Geopoint, Geoshape, Marking, Cipher. Arrays cannot contain nulls; nested arrays are not supported in OSv2; Geopoint is stored as a `lat,lon` string. [Fact] https://www.palantir.com/docs/foundry/object-link-types/properties-overview/ . All field types except Map and Binary are valid; all types can be arrays except Vector and Time series. [Fact] https://www.palantir.com/docs/foundry/object-link-types/base-types/
- **String options** in the code definition: `isLongText`, `supportsEfficientLeadingWildcard`, `supportsExactMatching`, `supportsFullTextRegex`, `supportsPhonetic`, `enableAsciiFolding`, `analyzerOverride`. Decimal defaults to precision 5, scale 2. [Fact] `osdk-ts/packages/maker/src/api/properties/PropertyTypeType.ts` . [Inference] Search behaviour is configured per property at index time, as in Elasticsearch mappings.
- **Vector.** Defined by `dimension` (at least 1), `supportsSearchWith` (one of `COSINE_SIMILARITY`, `DOT_PRODUCT`, `EUCLIDEAN_DISTANCE`), optional `embeddingModel` (text or multimodal), optional `quantization` (`NO_QUANTIZATION`, `BYTE`, `HALF_BYTE`, `BINARY`). [Fact] same file and `client.unstable/.../ontology-metadata/api/__components.ts`
- **Struct.** A single property with named typed fields, backed by one struct-typed column. No nesting; fields cannot be arrays, but a property can be an array of structs. Allowed field types: boolean, byte, date, decimal, double, float, geopoint, integer, long, short, string, timestamp. Indexed like Elasticsearch object fields, so conditions on an array-of-struct are evaluated per field independently (a query for first name A and last name B can match an object where two different elements each satisfy one condition). Not in OSv1. [Fact] https://www.palantir.com/docs/foundry/object-link-types/structs-overview/ . Structs can declare a "main value" (one or more fields) so the struct behaves like a simple value. [Fact] `PropertyTypeType.ts`; https://palantir.com/docs/foundry/ontology/ontology-structural-guidance/
- **Property reducers** (beta) collapse an array property to one display value (highest/lowest, latest/earliest, first/last, true-first/false-first; for struct arrays, by one field with chained tie-breakers). Queries still operate on the whole array; you cannot filter on the reduced value; reducers change instantly without reindexing; a reduced array can implement a non-array interface property. [Fact] https://www.palantir.com/docs/foundry/object-link-types/property-reducers/
- **Time series, geotemporal series, media reference, attachment.** These are references to data stored elsewhere (time series syncs, media sets, uploaded files), with dedicated API endpoints (for example `.../timeseries/{property}/firstPoint|lastPoint|streamPoints`, `.../media/{property}/content|metadata`, `.../attachments/{property}`). Media references need a media reference column and a configured media source. [Fact] https://www.palantir.com/docs/foundry/object-link-types/base-types/ ; endpoint paths from `foundry_sdk/v2/ontologies/*.py`
- **Cipher text** has encrypt and decrypt endpoints per property. [Fact] `foundry_sdk/v2/ontologies/cipher_text_property.py`
- **Edit-only properties** (OSv2 only) are not mapped to any column; values come only from edits; each must be "permissioned to" one of the type's backing datasets. You can later map them to a column. [Fact] https://www.palantir.com/docs/foundry/object-link-types/edit-only-properties/
- **Derived properties** (beta) are computed at query time from linked objects: follow up to three link hops, then aggregate with count, average, sum, min, max, approximate or exact cardinality, collect list or collect set (collect defaults to 10 values, max 100; filters and sorts see the full set, not just the returned values). A derived property cannot derive from another derived property. Not available on OSv1; restrictions apply to primary keys, required properties, value types and formatting. [Fact] https://www.palantir.com/docs/foundry/object-link-types/derived-properties/ . The code definition confirms the aggregation set and the 100 cap. [Fact] `ObjectTypeDatasourceDefinition.ts` . Derived properties cannot use internal indexes and may force in-memory or Spark execution even on small sets. [Fact] https://www.palantir.com/docs/foundry/ontologies/oss-limitations/ . Palantir's guidance: use them freely below roughly 10,000 objects per query, and above that consider documented denormalisation. [Fact] https://palantir.com/docs/foundry/ontology/ontology-structural-guidance/
- **Runtime derived properties.** Separately, any OSDK caller can add derived properties to an object set at query time with `withProperties`, for example a lead count computed by pivoting to a link and counting. [Fact] `osdk-ts/packages/api/src/objectSet/ObjectSet.ts`
- **Shared properties** are property definitions reused across object types: metadata is shared, data is not. Marked with a globe icon. [Fact] https://www.palantir.com/docs/foundry/object-link-types/shared-property-overview/
- **Value types** are semantic wrappers over a base type with optional constraints, scoped to a "space", permissioned and versioned, enforced in pipelines (Pipeline Builder) and the Ontology. Constraint kinds: enum (one-of, case-sensitive or not for strings), range (numeric, temporal, string length, array size), regex (optionally substring match), RID, UUID, uniqueness (array elements), nested (constraint applied per array element), element constraints (struct field → value type). Not available in the Default ontology. [Fact] https://www.palantir.com/docs/foundry/object-link-types/value-types-overview/ , https://www.palantir.com/docs/foundry/object-link-types/value-type-constraints/ . Exposed via `/v2/ontologies/{ontology}/valueTypes`. [Fact] `foundry_sdk/v2/ontologies/ontology_value_type.py`
- **Mandatory control properties** (OSv2): a property of type Mandatory Control, mapped to a marking column of a marking-backed restricted view, that secures the other properties in the same datasource row by row. Types: markings (user needs all), organizations (user needs at least one), both, or classifications (hierarchical; requires CBAC). Values must be non-null (empty array means no restriction), must fall within an allowed set declared on the datasource, and violations fail indexing or reject the action. Hidden by default. [Fact] https://www.palantir.com/docs/foundry/object-link-types/mandatory-control-properties/
- Other property sub-pages (value formatting, conditional formatting, render hints, type classes, required properties) were listed but not opened [Unverified].

### 4. Link types

Plain English: a link type is a named relationship between two object types. "Flight → assignedAircraft → Aircraft". One definition is traversable in both directions.

Technical detail:
- Each link type has two sides, each with its own display name and API name; multiple link types may connect the same pair; links cannot cross ontologies. [Fact] https://www.palantir.com/docs/foundry/object-link-types/link-types-overview/
- **Three implementations:** (a) foreign key: a property on one side holds the other side's primary key, giving one-to-many or one-to-one, and one-to-one is "not enforced"; (b) join table: a datasource with one column per side's primary key and one row per link, giving many-to-many, required for editing many-to-many links; (c) object-backed: a third "backing" object type with a many-to-one link to each endpoint, used when the relationship has its own data (role, dates, allocation). Link API names: lowercase first letter, alphanumeric, unique per object type, 1-100 characters, NFKC-normalised. [Fact] https://www.palantir.com/docs/foundry/object-link-types/create-link-type/ . In code these are `OneToManyLinkTypeDefinition` (with `manyForeignKeyProperty`, `cardinality: OneToMany | OneToOne`), `ManyToManyLinkTypeDefinition`, and `IntermediaryLinkTypeDefinition` (with `intermediaryObjectType`). [Fact] `osdk-ts/packages/maker/src/api/links/LinkType.ts`
- **Editing links.** Many-to-many links are created and deleted with link rules; foreign-key links are changed by modifying the foreign key property. [Fact] https://www.palantir.com/docs/foundry/action-types/rules/
- **Guidance:** use direct links when the relationship carries no metadata, object-backed links when it does; do not create links that exist only because two datasets share a key. [Fact] https://palantir.com/docs/foundry/ontology/ontology-structural-guidance/
- Index and storage: join tables are indexed alongside objects and count towards ontology volume, growing linearly with link count. [Fact] https://palantir.com/docs/foundry/ontologies/volume-usage/
- Bulk link loading in the OSDK (`experimental_asyncIterLinks`) returns at most 100,000 links per page of source objects and may return stale keys. [Fact] `osdk-ts/packages/api/src/objectSet/ObjectSet.ts`

### 5. Interfaces

Plain English: an interface is a shared shape, like "Facility" with a location and a manager, that several object types (Airport, Warehouse) implement, so one app or agent can work across all of them.

Technical detail:
- An interface has interface properties (defined locally, which Palantir recommends, or via shared properties), link type constraints, action type constraints, and metadata. Object types can implement many interfaces; interfaces can extend many interfaces. Interfaces are abstract: no datasets, no direct instances. Permissioned through Ontology roles. Support: full in Ontology Manager, Marketplace, TypeScript v2 functions; partial in Actions, Object Set Service (aggregation and interface links in development), OSDK (TypeScript yes; Java and Python in development), Workshop; not in TypeScript v1 or Python functions. [Fact] https://www.palantir.com/docs/foundry/interfaces/interface-overview/ (the feature table on https://www.palantir.com/docs/foundry/functions/language-feature-support/ agrees that Python functions lack interface support).
- **Interface link types** declare a link to an interface or a concrete object type, with cardinality `ONE` or `MANY` and a required flag; implementers satisfy them with concrete link types. [Fact] https://www.palantir.com/docs/foundry/interfaces/interface-link-types-overview/
- **Interface action type constraints** (beta) declare a capability (for example "Close") with typed parameter constraints that every implementer must map to one of its own concrete action types. Save-time validation blocks unmapped required constraints, incompatible types, or one parameter mapped twice. Constraints do not define logic, criteria or side effects; the OSDK resolves the concrete action for an object type and calls it. [Fact] https://www.palantir.com/docs/foundry/interfaces/interface-action-type-constraints/
- Action rules exist for create, modify and delete objects of an interface and create or delete links on interface objects. [Fact] https://www.palantir.com/docs/foundry/action-types/rules/
- In queries, `narrowToType` casts an object set between an interface and implementing types; the REST `ObjectSet` union includes `interfaceBase`, `asType`, `asBaseObjectTypes` and `interfaceLinkSearchAround`. [Fact] `ObjectSet.ts`; `foundry_sdk/v2/ontologies/models.py`
- Subscription updates on an interface object set arrive as the underlying object types; clients remap properties using `implementsInterfaces2` metadata. [Fact] https://www.palantir.com/docs/foundry/ontology-sdk/websocket-subscriptions/

### 6. Object sets and the query model

Plain English: an object set is a saved or ad hoc question such as "open orders over 10,000 for customers in Ohio". It is built by composing operations and is then paged, counted, aggregated or watched.

Technical detail:
- **Kinds of saved sets:** static (list of primary keys), dynamic (saved filter, re-evaluated), temporary (passed between services, creator-only, expires within 24 hours), permanent (stored for reuse). [Fact] https://www.palantir.com/docs/foundry/object-backend/overview
- **Wire format.** The public REST `ObjectSet` is a discriminated union: `base`, `static`, `reference`, `filter`, `union`, `intersect`, `subtract`, `searchAround`, `interfaceLinkSearchAround`, `nearestNeighbors`, `withProperties`, `asType`, `asBaseObjectTypes`, `interfaceBase`, `methodInput`. [Fact] `foundry_sdk/v2/ontologies/models.py` lines ~3607-3627. The internal OSS union is similar and adds `softLinkSearchAround`, `knn`/`knnV2`, `referenced`. [Fact] `client.unstable/src/generated/object-set-service/api/__components.ts`
- **Filters.** Public search query types: eq, gt/gte/lt/lte, in, isNull, and, or, not, contains, startsWith, containsAllTerms, containsAnyTerm, containsAllTermsInOrder (and prefix-on-last-term variant), regex, wildcard, interval, relative date range, within distance, within bounding box, within/intersects polygon, intersects / does not intersect bounding box, geoshape. [Fact] `models.py` `SearchJsonQueryV2`. OSDK string filters support fuzzy and phonetic options. [Fact] `osdk-ts/packages/api/src/aggregate/StringFilter.ts`. Internally OSS also has parameterised filters and a `userContext` filter. [Fact] OSS `ObjectSetFilter` union.

### 7. Action types in detail

Plain English: an action type is a form plus a transaction. "Assign Employee" takes an employee and a role, checks the submitter is in HR, updates two objects, adds a link, and emails the new manager.

Technical detail:
- **Anatomy (from code).** `apiName`, `displayName`, `description`, `icon`, `parameters`, `parameterOrdering`, `rules`, `sections`, `formContentOrdering`, `validation` (submission criteria), `isolationSettings` (isolation mode + retry settings), `entities`, `status`, `typeClasses`, display layout, `submissionMetadata` (button text, success message, undo button toggle), `permission`. [Fact] `osdk-ts/packages/maker/src/api/action/ActionType.ts`, `SubmissionMetadata.ts`. The internal level validation also carries `readAuthorization` and `writeAuthorization`. [Fact] `ActionTypeLevelValidation` in OMS `__components.ts`
- **Parameters.** Types include boolean, integer, long, double, decimal, string, timestamp, date, geohash, geoshape, attachment, marking, media reference, time series reference, geotime series reference, object reference, object set, interface reference, struct, object type reference, each with a list variant where applicable. [Fact] `maker/src/api/action/ActionParameterType.ts`. Allowed-value constraints: one-of (with or without "other values allowed"), range, text (min/max length, regex), datetime range, object query (dropdown filtered by an object set), user (optionally from groups), multipass group, and others. [Fact] `ActionParameterAllowedValues.ts`; validation responses echo constraint kinds `arraySize`, `groupMember`, `objectPropertyValue`, `objectQueryResult`, `oneOf`, `range`, `stringLength`, `stringRegexMatch`. [Fact] `osdk-ts/packages/api/src/actions/ActionResults.ts`. Each parameter can be visible or hidden, editable or fixed, use a value type, be pre-filled by the host app, read an object's current property value, and override later parameters' configuration. [Fact] https://www.palantir.com/docs/foundry/action-types/parameter-overview/ . Conditional overrides exist for parameters and sections. [Fact] `ActionParameterConditionalOverride.ts`, `SectionConditionalOverride.ts` (contents not read in detail).
- **Rules.** Ontology rules: create object (primary key required), modify object(s), create-or-modify, delete object(s), create link(s), delete link (many-to-many only; foreign-key links use modify), function rule (if present, no other rules allowed), and five interface rules. Other rules: notification, webhook, schedule (trigger a build, edits applied after build starts). Each property value comes from a parameter, a property of an object parameter, a static value, or current user/time; the time is fixed at execution start. Rules compile into one edit per object, so order matters and later rules override earlier ones; you cannot modify or delete an object created in the same action, or create the same object twice. [Fact] https://www.palantir.com/docs/foundry/action-types/rules/ . Code adds value sources `uniqueIdentifier`, `synchronousWebhookOutput` (use the writeback webhook's response), `scheduleRunRid`, and a `scenarioRule`. [Fact] `OntologyIrLogicRuleValue` and `OntologyIrLogicRule` unions in OMS `__components.ts`
- **Submission criteria** (formerly validations). Conditions compare a left value (current user ID, group IDs including inherited, user attributes; a parameter or a property of an object parameter, or a list length; execution context = "in a scenario or not") to a parameter, static value or "no value". Operators: is, is not, matches, less than, greater than or equals; for lists: includes, includes any, is included in, each is, each is not. Logical nodes require all, any or none of children and nest. Each root-level node has its own failure message, shown in every app. Evaluated at submission with the state at that moment; object set and attachment parameters cannot be used. Palantir warns against `NOT` conditions on group, marking or organisation membership because scoped tokens may lack the attribute and the `NOT` then passes. [Fact] https://www.palantir.com/docs/foundry/action-types/submission-criteria/
- **Validation API.** Apply with `mode: VALIDATE_ONLY` (REST) or `$validateOnly: true` (OSDK) returns per-criterion and per-parameter VALID/INVALID with evaluated constraints and configured failure messages. [Fact] `models.py` `ApplyActionMode`; `ActionResults.ts` `ValidateActionResponseV2`
- **Side effects.** Notifications: recipients static, from a parameter, from an object property holding user or group IDs, or from a function; content from a template (subject ≤ 250 chars, body ≤ 1,000, custom email HTML ≤ 51,200) or a function returning a `Notification`; data rendered reflects the state before the edits; up to 500 recipients (50 if function-rendered); by default every recipient must be able to see the rendered data or the action fails, with an option to notify only permitted recipients; no direct email addresses; email redaction settings may replace content. [Fact] https://www.palantir.com/docs/foundry/action-types/notifications/ . Webhooks: see finding 4; inputs mapped from parameters, static values or object properties, or produced by a function; a function can return a list of payloads to fire a side-effect webhook many times; only writeback webhooks have outputs usable by later rules; OAuth 2.0 token handling done by the platform for REST sources with an outbound application. [Fact] https://www.palantir.com/docs/foundry/action-types/webhooks/ . Side effects run only if submission criteria pass; failed notifications do not block edits; configuring webhooks needs extra Data Connection permissions. [Fact] https://www.palantir.com/docs/foundry/action-types/permissions/
- **Function-backed actions.** For edits too complex for rules (close an incident and all its alerts; compute a value from several objects; create several linked objects). [Fact] https://www.palantir.com/docs/foundry/action-types/function-actions-overview/ . **Batched execution**: the function takes one parameter that is a list of structs, so a batch of N action calls becomes one function execution instead of N sequential executions. [Fact] https://www.palantir.com/docs/foundry/action-types/function-actions-batched-execution/
- **Consistency.** Atomic commit of Ontology edits (not side effects); consistency = value type constraints and required properties enforced; write modes "batched" (reads never see own uncommitted edits) or "staged" (reads, searches and aggregations see own edits; TS v2, Python, AIP Logic only; legacy isolation only). Isolation levels: legacy, snapshot (default for new batched actions; one point-in-time view; fails if a written object changed; does not catch write skew, so route invariants through a shared object), read committed (last committer wins per property). Parameters with defaults count as writes. Retries: up to 5 attempts on transient errors, by default only for actions without external calls (webhooks, Data Connection, OSDK calls from functions, calls to other functions/actions); configurable per action type. [Fact] https://www.palantir.com/docs/foundry/action-types/consistency-guarantees/ . Version checks: OSv2 checks only versions of objects used to generate edits against edited objects, fewer `StaleObject` conflicts, weaker guarantees. [Fact] https://www.palantir.com/docs/foundry/object-edits/how-edits-applied/
- **Undo / revert.** Only the submitting user, only from the success toast, only if the action is still the most recent edit to every affected object, only on OSv2, and only if "Allow revert" was on at submission (default on for actions created after May 2024 that touch only OSv2 types). Side effects are not undone. [Fact] https://www.palantir.com/docs/foundry/action-types/action-reverts/
- **Batch apply.** REST `applyBatch` accepts up to 20 actions per call, higher for OSv2-only actions without functions; notifications are not supported on that endpoint; parameter default values are not applied by the apply endpoint. [Fact] `foundry_sdk/v2/ontologies/action.py` docstrings. Docs: up to 10,000 calls in one batch, 20 for non-batched function-backed actions, edits in a batch count as one group against limits. [Fact] https://www.palantir.com/docs/foundry/action-types/scale-property-limits/ . The two sources state different headline batch numbers; the docs page is per-application ("additional limits may apply, depending on the calling application") and the API docstring is for the REST endpoint. [Inference]
- **Return edits.** `returnEdits: ALL | ALL_V2_WITH_DELETIONS | NONE` (default none). Response lists added, modified, deleted objects and added and deleted links, or `largeScaleEdits` with no detail. [Fact] `models.py` `ReturnEditsMode`; `ActionResults.ts`. Overrides allow fixing `uniqueIdentifierLinkIdValues` and `actionExecutionTime`. [Fact] `models.py` `ApplyActionOverrides`. Apply accepts `branch` and `scenarioRid`. [Fact] `action.py`. OSv2 edits are visible immediately after the action completes; OSv1 edits were eventually consistent. [Fact] `action.py` docstring

### 8. Action and object permissions

Plain English: three separate questions: can you see this kind of thing, can you see these specific things, and may you perform this operation on them with these inputs?

Technical detail:
- **Project-based permissions** (current model): ontology resources are saved in projects; project roles (Viewer, Editor, Owner) govern who can view, edit and manage them; markings or roleless projects hide them. Viewing an object type's schema needs View on the object type, not on the datasource; seeing objects additionally needs data access via object/property security policies or View on the backing datasource. Editing a link needs edit on the link type and both object types; editing or running an action needs edit on the action type and all edited resource types. The legacy model used Ontology `viewer`/`editor`/`owner` roles managed in Ontology Manager, and before that permissions derived from datasources. [Fact] https://www.palantir.com/docs/foundry/object-permissioning/ontology-permissions/
- **Applying an action** requires: view on the edited types and their datasources; passing submission criteria; for types editable "only via actions" (the default for new types) only Read on edited objects, which means users can create objects they cannot view; for types editable by other means, Edit on the writeback dataset (discouraged because Edit exposes all writeback data); passing a restricted view's edit policy; permissions on the action log type if enabled. Read-time policies (restricted views, object and property security policies) filter what an action can read but not what it writes. [Fact] https://www.palantir.com/docs/foundry/action-types/permissions/
- **Multi-datasource checks:** create needs view on the datasources whose properties are set; modify needs view of existing values of the edited properties (others appear null during validation); delete needs view of the whole object; links need ability to load both objects. [Fact] https://www.palantir.com/docs/foundry/object-edits/permission-checks/
- **Read and write authorizations** on action types: a read boundary limits which marked data an action may load even if the user could; a write boundary enforces a minimum security level on created or modified data; if they differ, declassification permission is checked at save/publish time. Platform-managed writes (action logs, edit history) are exempt. [Fact] https://www.palantir.com/docs/foundry/action-types/read-write-authorizations/
- **Object and property security policies:** row-level (object policy) and column-level (property policies) combine to cell-level; primary key cannot be in a property policy; each property in at most one property policy; granular policy comparison weight ≤ 10,000 (object policy alone, or object policy plus one property policy). Policy conditions in code: and/or, static group membership, user's groups match a property, marking property. Recommended over restricted views (cell level, near-instant updates, streaming and branching support). Editing policies needs project Owner. A "Test security policies" modal previews what a chosen user would see. [Fact] https://www.palantir.com/docs/foundry/object-permissioning/object-security-policies/ ; `maker/src/api/object/SecurityCondition.ts`
- Palantir's design guidance: start restrictive; one object type with policies, not duplicated types per audience; avoid ad hoc filtering in application code. [Fact] https://palantir.com/docs/foundry/ontology/ontology-structural-guidance/

### 11. Backend services

Plain English: one service stores the definitions, one pipeline keeps a search index in sync with the source data and the edits, one database serves the index, one service answers all queries, and one service applies actions.

Technical detail:
- **Ontology Metadata Service (OMS)** holds object, link and action type definitions. [Fact] https://www.palantir.com/docs/foundry/object-backend/overview . Its generated client shows endpoints such as `loadOntology`, `loadAllOntologyEntities`, `bulkLoadOntologyEntities`, `getLinkTypesForObjectTypes`, `getActionTypesForObjectTypes`, `getObjectTypesForInterfaceTypes`, `loadOntologyDatasources`, `modifyOntology`, `loadMergedRebaseState`, plus separate search, workflow, security-provenance and an "Ontology LLM" plugin service. [Fact] `osdk-ts/packages/client.unstable/src/generated/ontology-metadata/api/OntologyMetadataService/*.ts` . [Inference] Definitions are versioned entities modified through one `modifyOntology` call, with branch and rebase state stored in OMS.
- **Object Set Service (OSS)** serves all reads (search, filter, aggregate, load) for every app. [Fact] overview page. Generated client sub-services: ObjectSetService (create, temporary create, get, page, materialize), VersionedObjectSetService (saved sets with versions), ObjectSetAggregationService, ObjectSetScrollService, ObjectSetSuggestService. [Fact] `client.unstable/src/generated/object-set-service/api/`
- **Object databases.** OSv1 (Phonograph): one system for indexing, querying and edits; deprecated, planned unavailable after 30 June 2026. OSv2: indexing and querying separated for horizontal scale; incremental indexing default; "tens of billions" of objects per type [Vendor claim]; 2,000 properties per type; 10,000 objects per action; streaming datasources; Spark-backed search-around; schema migrations of edits. [Fact] https://www.palantir.com/docs/foundry/object-backend/overview
- **Actions service** applies edits to object databases and builds the action log. [Fact] same page.
- **Object Data Funnel ("Funnel")** orchestrates all writes into OSv2: reads datasets, restricted views, streams and action edits; indexes them; keeps them current. [Fact] same page.
- **Batch pipeline stages:** (1) changelog: diff new source transactions into Funnel-owned APPEND changelog datasets; (2) merge: join changelogs with recent action edits on primary key; (3) index: one job per object database writes index files; (4) hydration: search nodes download index files to local disk, after which the type is queryable. **Live** pipelines run on each source update and every 6 hours if edits exist; **replacement** pipelines are built in the background for schema changes and swap in after a successful run. Full reindex triggers: more than 80% of rows changed in one transaction, a schema change, or manual request. Incremental inputs must have at most one row per key per transaction; deletes need a declared deletion column (a column named `is_deleted` is not enough); Iceberg tables must be unique per key or a full reindex fails. [Fact] https://www.palantir.com/docs/foundry/object-indexing/funnel-batch-pipelines/
- **Streaming pipelines:** seconds-to-minutes latency; changelog streams with "most recent update wins" in stream order, so partition by key and order by event time upstream; full-row records only; exactly-once (default) or at-least-once; max record 1 MB; max 250 properties; no MDOs; no user edits; no materializations; cannot be cancelled; 2 MB/s indexing throughput per object type; Flink checkpointing every 1 s dominates latency; invalid records are dropped rather than failing; retention windows are best-effort with a two-weekly replacement replay. [Fact] https://www.palantir.com/docs/foundry/object-indexing/funnel-streaming-pipelines/ , https://www.palantir.com/docs/foundry/object-indexing/faq/
- **Direct datasources** (beta): low-latency direct writes from Pipeline Builder, supporting edits on stream-backed types and an optional source-timestamp ordering (older writes dropped). Replay wipes and repopulates the object view. [Fact] https://www.palantir.com/docs/foundry/object-indexing/direct-datasources/
- **Retries and size:** transient indexing errors retry after about 5 minutes; terminal errors wait for new data; index size is bounded by search-node disk. [Fact] https://www.palantir.com/docs/foundry/object-indexing/faq/
- **Monitoring:** "Sync Propagation Delay" rules alert when freshness exceeds a threshold. [Fact] funnel batch page.

### 12. How user edits merge with datasource data (and writeback)

Plain English: the source system says the order status is "shipped"; an operator corrects it to "returned". Which wins tomorrow when the source reloads?

Technical detail (all [Fact] from https://www.palantir.com/docs/foundry/object-edits/how-edits-applied/ unless noted):
- Edits are enabled per object type. An action writes to the index immediately; Funnel queues each edit with offset tracking (supporting concurrent edits) and periodically flushes them into a Funnel-owned merged dataset. Read-after-write is guaranteed once the modification is sent.
- Merge builds run when a new source transaction lands, or every 6 hours if edits exist.
- **Strategy 1 (default) "apply user edits":** edited properties keep the edit forever; unedited properties follow the source. If a source row disappears, the object leaves the Ontology unless it was created by a user edit; if the row returns, earlier edits reapply. A user-created object takes properties only from the create edit; later source values for those properties are ignored; unset properties are null.
- **Strategy 2 "apply most recent value"** (OSv2): requires a UTC timestamp column in the source; per property, an edit applies only if its time is later than the source timestamp. Edit-only properties always apply; null source timestamps mean edits always apply; changing the timestamp via an edit does not count. Multi-datasource types: each property follows its datasource's strategy.
- **Deletes** are not edits; a deleted object stays hidden whatever the source says; recreation does not inherit edits; modifying a deleted object fails.
- Individual edits cannot be reverted except via the toast; "drop all edits" resets a type to source.
- **Writeback / materializations.** OSv1 needed a writeback dataset for edits; OSv2 does not. OSv2 materializations are optional datasets (or restricted views) of current state (source + edits), schema = property API names; automatic mode propagates edits in minutes, periodic mode on new data or every 6 hours; only the latest snapshot is retained; `__`-prefixed columns are internal. Multiple materializations per type allowed (for example property subsets). [Fact] https://www.palantir.com/docs/foundry/object-edits/materializations/
- **External writeback** is the webhook mechanism in actions (section 7), not the dataset.

### 13. Schema evolution, Ontology Manager, branching and proposals

Plain English: changing the model is a governed change process, like code review, because apps and agents depend on it.

Technical detail:
- **Ontology Manager** is the UI for types, datasources, properties, security, materializations, capabilities (action logs) and statuses; saving stages then commits changes; "History" allows reverting saved changes. [Fact] create-object-type page; schema-migrations page.
- **Breaking changes** on types with edits: changing input datasources, primary key, property data type, property ID with edits, deleting a property or struct field with edits, changing a struct field type. Non-breaking: display name, title key, render hints, type classes, visibility; changes to never-edited properties. Saving is blocked until each breaking change has a migration: drop property/field/all edits, move edits, cast (a fixed cast matrix, for example String→Integer/Long/Double/Boolean/Date/Timestamp/Geopoint/Geoshape), backfill a value (only on user-created objects, never overwriting), revert migration. Saving creates a new schema version and a replacement pipeline; the new version becomes queryable after hydration. Max 500 migrations at once; none on the primary key. [Fact] https://www.palantir.com/docs/foundry/object-edits/schema-migrations/
- **Branching.** Ontology branches integrate with Foundry Global Branching; branches are created only from main; object, action, link, interface and shared property types can be "protected" so changes must go via a branch; indexing on a branch makes test data available; branches rebase automatically until they contain ontology changes, then manually with a per-resource choice (main, branch, custom); a Global Branching proposal creates an ontology proposal with reviewers who approve or reject individual resource tasks; merge requires policy approval and passing checks; indexing on a protected resource itself requires approval. Known merge failures include keeping a branch version of a datasource that main removed. [Fact] https://palantir.com/docs/foundry/ontologies/branching-ontology/ . The REST API accepts a `branch` on action apply. [Fact] `foundry_sdk/v2/ontologies/action.py`
- **Scenarios** are sandboxed what-if edit layers: REST endpoints create scenarios, list edited objects and links, find conflicts and rebase; actions can be applied within a scenario and submission criteria can test "in a scenario". [Fact] `foundry_sdk/v2/ontologies/ontology_scenario.py`; https://www.palantir.com/docs/foundry/action-types/submission-criteria/

### 16. Ontology MCP

Plain English: a switch that turns a Developer Console app into an MCP server, so Claude, Copilot or any MCP client can read objects and call actions under the same rules as the app.

### 17. Cost model and performance

- Query minimums since 1 January 2026: base 2, search-around 5, aggregation 5, Ontology SQL 5, advanced (semantic search) 10, derived property 10, action 18 + 1 per extra edited object, OSv1 16 compute-seconds. Compute is charged to the originating app; for Object Explorer and the OSDK it is charged to the queried object types, split evenly across types. Legacy (pre-2026): OSv2 query 4, function on objects 4, action 18. [Fact] https://palantir.com/docs/foundry/ontologies/query-compute-usage/
- Indexing compute = (driver + executors) × max(vCPU, GiB ÷ 7.5) × wall-clock seconds; drivers: records, properties, property size, update frequency; changelog (incremental) indexing can give "orders-of-magnitude" savings. [Fact] https://palantir.com/docs/foundry/ontologies/compute-usage/
- Volume: hourly measurement of index size per object type plus join tables, averaged to GB-months; ontology data is not compressed, so it can exceed dataset size. [Fact] https://palantir.com/docs/foundry/ontologies/volume-usage/
- Guidance: filter first, query single object types rather than multi-type searches, keep object sets small. [Fact] query compute page.

### 18. Modelling in practice: Palantir's guidance

- **Checklist:** model reality not systems; curate properties; collaborate across teams; one entity per type; actions for human or agent decisions, pipelines for automated transforms; interfaces for shared shape; document decisions; validate against real questions. **Principles in priority order:** domain-driven design; DRY with a "rule of three"; open for extension, closed for modification; composition over deep hierarchies (capability interfaces like `Schedulable`, `Inspectable`). Pragmatism: name trade-offs (for example denormalisation acceptable until about 10,000 objects), protect naming, semantics and security as hard-to-fix invariants. [Fact] https://palantir.com/docs/foundry/ontology/ontology-best-practices/
- **Anti-patterns:** system silos, kitchen sink (all columns), department silos, god object, golden hammer (one tool for everything), action sprawl (warning sign: more than 10 action types on one object type; design actions around business operations like "Transfer Employee"), time machine (versions as objects), misnomer (vague names). [Fact] https://www.palantir.com/docs/foundry/ontology/ontology-anti-patterns
- **Structural guidance:** store each fact once; pre-compute same-object values in pipelines, use derived properties for link-dependent values; group related fields into structs (including LLM outputs with confidence and reasoning); interfaces even if a workflow must be duplicated temporarily; object-backed links for relationship metadata; names readable by humans and agents; security in domain terms. [Fact] https://palantir.com/docs/foundry/ontology/ontology-structural-guidance/
- **Validation drills:** questions sourced from the organisation's operating rhythm, structured situation → contributing factors → impact; run by non-builders in general tools only; record correctness, time, hesitation, search terms, dead ends, manual exports; diagnose with a symptom table; then rerun with an AI agent without path hints and compare; keep the questions as a standing evaluation suite. [Fact] https://palantir.com/docs/foundry/ontology/ontology-design-validation/

## What to copy

1. **Definitions as a versioned, typed IR separate from data.** Store object types, properties, links, interfaces, value types and action types as JSON definitions with stable IDs, API names, display names, descriptions, aliases, status and visibility, edited by a single `modifyOntology`-style call that produces a new version. Model it on the `@osdk/maker` types. Why: agents and apps bind to API names; the IR is the product's core asset. Source: `osdk-ts/packages/maker/src/api/`, https://www.palantir.com/docs/foundry/object-link-types/object-type-metadata/
2. **Primary key discipline.** Require a deterministic string or integer key per object type, reject duplicates at index time (fail the sync, never silently merge), and attach edits and links to key values. Source: https://www.palantir.com/docs/foundry/object-link-types/create-object-type/
3. **Status lifecycle with enforced rules.** experimental → active → deprecated (reason + deadline + replacement) plus example and promoted; block deletion and API-name changes on active; propagate status from object types to links. Agents should by default see only active and promoted types. Source: https://www.palantir.com/docs/foundry/object-link-types/metadata-statuses/
4. **Three link implementations.** Foreign key (1:1, 1:N), join table (N:M, editable), object-backed (relationship with its own properties). One link definition, two named directions. Source: https://www.palantir.com/docs/foundry/object-link-types/create-link-type/
5. **Value types with the documented constraint set** (enum, range, regex, UUID, RID, array uniqueness, nested, struct element), enforced on sync and on every action. Source: https://www.palantir.com/docs/foundry/object-link-types/value-type-constraints/
6. **Object set algebra as the only read API.** Implement the union (base, static, filter, union, intersect, subtract, searchAround, nearestNeighbors, withProperties, interface cast) as JSON, with the filter operator list from `SearchJsonQueryV2`, aggregations (count, min, max, avg, sum, exact and approximate distinct, percentile) with an accuracy flag in the response, `select` projection and page tokens. Give agents this, not SQL over raw tables. Source: `foundry_sdk/v2/ontologies/models.py`; https://www.palantir.com/docs/foundry/object-backend/aggregation-considerations/
7. **Published hard limits from day one.** Copy the shape (in-memory cap, larger-engine fallback, absolute caps, "estimate exceeds limit by 2x → fail early"). At small-company scale, start with 10,000 objects per action, 100,000 per search-around, 1,000 default page size. Source: https://www.palantir.com/docs/foundry/ontologies/oss-limitations/ , https://www.palantir.com/docs/foundry/action-types/scale-property-limits/
8. **Action types as the only write path for agents and staff.** Definition = typed parameters with allowed-value constraints + ordered rules (create, modify, create-or-modify, delete, link, unlink, function) + submission criteria tree + side effects + isolation and retry settings + success message + undo toggle. Rules compile to one edit per object; forbid modify-after-create in the same action. Source: https://www.palantir.com/docs/foundry/action-types/rules/ , `maker/src/api/action/ActionType.ts`
9. **Submission criteria as a boolean tree with per-node failure messages,** evaluated at submit time on user attributes, group membership and parameter/object values; forbid `NOT` on membership checks. Return these messages to the agent so it can explain refusals. Source: https://www.palantir.com/docs/foundry/action-types/submission-criteria/
10. **Validate-only mode.** Every action endpoint supports a dry run returning per-criterion and per-parameter results. Agents should validate, show the human, then execute. Source: `models.py` `ApplyActionMode`; `ActionResults.ts`
11. **Transaction semantics:** atomic edits, snapshot isolation by default with object-level conflict detection, optional read-committed, up to 5 automatic retries only when the action has no external calls, idempotent re-runs. Source: https://www.palantir.com/docs/foundry/action-types/consistency-guarantees/
12. **Two-mode external writeback.** One blocking pre-commit webhook whose response can feed later rules; any number of post-commit best-effort webhooks; document the "external succeeded, commit failed" gap and reconcile. Source: https://www.palantir.com/docs/foundry/action-types/webhooks/
13. **Notifications with recipient permission checks:** every recipient must be allowed to see rendered data, or the action fails (or only permitted users get it); render pre-edit state; caps on recipients and lengths. Source: https://www.palantir.com/docs/foundry/action-types/notifications/
14. **Action log as first-class objects** with the documented schema (action ID, type, version, time, actor, edited keys, side-effect IDs, revert status, chosen parameters, extra context properties, human summary), linked to edited objects, and an option to require logs for an object type. Add an `actor_kind` (human or agent) and the agent's model and prompt reference [Inference]. Source: https://www.palantir.com/docs/foundry/action-types/action-log/
15. **Per-object edit history** separate from the decision log. Source: https://www.palantir.com/docs/foundry/object-edits/user-edit-history/
16. **Edit overlay with explicit conflict strategy per datasource:** "edits win" default and "most recent timestamp wins" opt-in, sticky deletes, user-created objects survive source deletion. This lets the product sit on top of a company's existing systems without owning them. Source: https://www.palantir.com/docs/foundry/object-edits/how-edits-applied/
17. **Incremental sync pipeline in four stages** (changelog diff, merge with edits on key, index, hydrate) with live and replacement pipelines, full reindex above an 80% change threshold, and a freshness alert. A small-scale version can be Postgres plus a search index. Source: https://www.palantir.com/docs/foundry/object-indexing/funnel-batch-pipelines/
18. **Breaking-change migrations for edits** (drop, move, cast, backfill, revert) blocking save until defined. Source: https://www.palantir.com/docs/foundry/object-edits/schema-migrations/
19. **Separate metadata permission from data permission,** and implement row (object policy), column (property policy) and cell security with null-out semantics, plus per-row marking columns. Provide a "test as user X" preview. Source: https://www.palantir.com/docs/foundry/object-permissioning/object-security-policies/ , https://www.palantir.com/docs/foundry/object-link-types/mandatory-control-properties/
20. **Token scope = user ∩ app restrictions ∩ requested operations;** no-scope tokens get nothing. Each agent is an "application" with an explicit list of object types, actions and functions. Source: https://www.palantir.com/docs/foundry/developer-console/application-restrictions/
21. **MCP exposure pattern:** one tool per action type (parameters become the tool schema, with an editable agent-facing description), one tool per query function, and one read tool over permitted object types; per-user OAuth for internal assistants and client credentials for headless agents. Source: https://www.palantir.com/docs/foundry/ontology-mcp/sample-architecture/ , https://www.palantir.com/docs/foundry/ontology-mcp/mcp-tools-and-agent-configuration/
22. **Read-only query functions with stable API names** distinct from edit functions; edit functions return proposed edits that only an action commits; declare edit provenance. Source: https://www.palantir.com/docs/foundry/functions/query-functions/ , https://www.palantir.com/docs/foundry/functions/edits-overview/
23. **Vector properties declared in the schema** (dimension, similarity function, embedding model, quantisation) and a `nearestNeighbors(text|vector, k≤500, property)` set operation that composes with filters. Source: `maker/src/api/properties/PropertyTypeType.ts`, `ObjectSet.ts`
24. **Change subscriptions** with ADDED_OR_UPDATED / REMOVED events, refresh signal, and back-pressure message. Source: https://www.palantir.com/docs/foundry/ontology-sdk/websocket-subscriptions/
25. **Branch, review, merge for model changes,** with protected resources requiring review. Source: https://palantir.com/docs/foundry/ontologies/branching-ontology/
26. **Bake in Palantir's modelling checklist and validation drill** as onboarding: interview-first domain model, anti-pattern linting (for example warn when an object type has more than 10 actions or many null-heavy properties), and an evaluation suite of real business questions run by both people and the agent. Source: https://palantir.com/docs/foundry/ontology/ontology-best-practices/ , https://www.palantir.com/docs/foundry/ontology/ontology-anti-patterns , https://palantir.com/docs/foundry/ontology/ontology-design-validation/
27. **Metered cost per operation type** mirroring Palantir's minimums, so heavy agent usage (search-arounds, semantic search) is visible to customers. Source: https://palantir.com/docs/foundry/ontologies/query-compute-usage/

## What cannot or should not be copied

- **Funnel's Spark and Flink machinery and "tens of billions" scale.** It exists for Palantir's largest customers. A 100-1,000 person company will have thousands to low millions of objects; Postgres with JSONB plus a search or vector index is enough. [Inference]
- **Foundry's dataset, transaction and lineage substrate.** The Ontology assumes every source is already a versioned Foundry dataset or stream with transactions (changelog diffs depend on it). The founder will connect to SaaS APIs and databases directly and must build simple change capture instead. [Inference]
- **The marking, CBAC and organisation security stack.** Classification hierarchies and mandatory markings are built for government and regulated sectors. Copy row/column/cell policies and per-row ACL columns; skip classifications unless a customer demands them. [Inference]
- **Workshop, Object Explorer, Quiver, Vertex.** Palantir's UI layer is large; object views and the action form can be generated from metadata instead. [Inference]
- **OSv1 behaviour** (latest-timestamp-wins changelogs, writeback datasets as required, eventual consistency). Deprecated. [Fact] https://www.palantir.com/docs/foundry/object-backend/object-storage-v2-breaking-changes/
- **Three function runtimes.** Supporting TS v1, TS v2 and Python is a legacy artefact; pick one runtime (TypeScript or Python) for customer logic. [Inference]
- **Palantir's names and branding** ("Ontology", "OSDK", "AIP") must not be used; the concepts are generic, but the trademarks are not. [Inference]
- **Approximate-by-default aggregations.** Palantir defaults some UIs to speed over accuracy; an agent product that reports numbers to staff should default to exact results at small scale and expose an accuracy flag. [Inference based on https://www.palantir.com/docs/foundry/object-backend/aggregation-considerations/]
